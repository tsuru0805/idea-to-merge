# 通用红线

红线是「做工方反复触、所以审查方重点盯」的事。下面是**和具体项目无关、几乎人人适用**的三条。
你应该按自己项目补充项目专属红线(比如「某某核心模块永不接外部依赖」)。

> 红线被触发**不自动等于错**,但审查方必须**显式点出来 + 按高风险对待**。

---

## R1 · 隔离分支红线

- 动代码前先开**隔离分支 / worktree**(`feature/<name>` 或 `git worktree add`),不在主干本体直接 commit。
- 审查方看到改动直接落在主干、没走隔离分支 → 立刻报。

**为什么**:主干是大家共享的稳定面。直接在主干上改,一旦出问题没有干净的回退点,也容易和别人的改动撞车。

---

## R2 · 破坏性命令护栏

下列命令执行前必须**三确认**:

- `rm` / `rm -rf` / `truncate` / `> file`(清空文件)
- `DROP TABLE` / 任何删库删表
- `git reset --hard` / `git clean -fd`
- 停服务 / `kill <pid>`

**三确认协议**:

1. 先 `pwd` + `ls` 确认当前目录和目标的**绝对路径**(即便看着是相对路径也展开看);
2. 路径若命中**生产数据 / 数据库 / 密钥 / 持久状态**任一,**停下来问人**;
3. 测试场景一律用 `/tmp/*` 隔离,生产路径不允许做默认值。

审查方看到破坏性命令 → 核它是否做了三确认、是否问过人。

**为什么**:这条是用真事故换来的——「我先测一下」的随手命令,在错误的目录里就是生产事故。
开发体验不为这条变复杂,但每个破坏性命令前停一下问自己一句。

---

## R3 · 反「轻描淡写」

- 做工方说「已完成 / 没问题 / 已修复」→ 审查方**独立验证**,不接受口头结论。
- 裁决和回应里要有**具体证据**:`文件:行号` / 命令输出 / 测试结果。
- 含糊词(「应该 / 大概 / 我觉得 / 基本上」)出现频率高 → 报。
- 完成度声明必须按[完成层级](truth-hierarchy.md)拆开,不许把「代码写完」说成「跑通了」。

**为什么**:模型(和人)都倾向于把进度说得比实际好。这条逼出「证据,不是说辞」。

---

## 怎么加你自己的红线

格式就照上面:**触发条件 + 审查方怎么核 + 为什么**。
好的红线都来自真实踩坑——别凭空想,等踩到一次、痛过一次,再把它钉成红线,这样它有牙。
