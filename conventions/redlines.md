# 通用红线

红线是「做工方反复触、所以审查方重点盯」的事。下面 R1–R3 **和具体项目无关、几乎人人适用**;
R4–R6 是后来疼出来的,各自标了适用前提(标签含义见[参考页](../docs/reference.md#怎么用这个仓)),按需取用。
你应该按自己项目补充项目专属红线(比如「某某核心模块永不接外部依赖」)。

> 红线被触发**不自动等于错**,但审查方必须**显式点出来 + 按高风险对待**。

---

## R1 · 隔离分支红线

- 动代码前先开**隔离分支 / worktree**(`feature/<name>` 或 `git worktree add`),不在主干本体直接 commit。
- 审查方看到改动直接落在主干、没走隔离分支 → 立刻报。

**为什么**:主干是大家共享的稳定面。直接在主干上改,一旦出问题没有干净的回退点,也容易和别人的改动撞车。

---

## R2 · 破坏性命令护栏

下列命令执行前必须**三确认**:

- `rm` / `rm -rf` / `truncate` / `> file`(清空文件)
- `DROP TABLE` / 任何删库删表
- `git reset --hard` / `git clean -fd`
- 停服务 / `kill <pid>`

**三确认协议**:

1. 先 `pwd` + `ls` 确认当前目录和目标的**绝对路径**(即便看着是相对路径也展开看);
2. 路径若命中**生产数据 / 数据库 / 密钥 / 持久状态**任一,**停下来问人**;
3. 测试场景一律用 `/tmp/*` 隔离,生产路径不允许做默认值。

审查方看到破坏性命令 → 核它是否做了三确认、是否问过人。

**为什么**:这条是用真事故换来的——「我先测一下」的随手命令,在错误的目录里就是生产事故。
开发体验不为这条变复杂,但每个破坏性命令前停一下问自己一句。

---

## R3 · 反「轻描淡写」

- 做工方说「已完成 / 没问题 / 已修复」→ 审查方**独立验证**,不接受口头结论。
- 裁决和回应里要有**具体证据**:`文件:行号` / 命令输出 / 测试结果。
- 含糊词(「应该 / 大概 / 我觉得 / 基本上」)出现频率高 → 报。
- 完成度声明必须按[完成层级](truth-hierarchy.md)拆开,不许把「代码写完」说成「跑通了」。

**为什么**:模型(和人)都倾向于把进度说得比实际好。这条逼出「证据,不是说辞」。

---

## R4 · 检查与动作同一条命令

`有长驻服务` `有部署` `多 session`

- 「先检查、再动作」的操作(查在途流量 → 重启;核 HEAD → 发布;核没人占用 → 删除),检查和动作**写进同一条 shell 命令**,用 `if / else` 绑定,检查不过动作就不发生:

  ```bash
  if [ "$(查在途数量)" = "0" ]; then 重启服务; else echo "有在途,不重启" >&2; false; fi
  ```

  用 `if / else`,别写 `检查 && 动作 || echo`——后者在动作本身失败时也会走到 `echo`,误报原因并返回 0。

- **守卫命令永不接管道**(`guard.sh | tail` 会吞掉守卫的退出码),要么 `set -o pipefail`。
- 审查方看到检查和动作分成两条命令、或守卫后面接了管道 → 报。

**为什么**:中间哪怕隔十几秒,世界就可能变了——查完在途 = 0 去写汇报,回来重启时正好切断了新一轮请求;核完要发布的提交,几分钟后发布时别的会话已经合入了十几个提交,一起被发了出去。检查没有原子性 = 没检查。

---

## R5 · 时机类动作只认人当次的字面许可

`通用`

- 重启、发布、出包、花钱(任何按量计费的调用,一毛钱也算)——**只认人在当前对话里的字面许可**,许可一次一发,不留存。唯一例外:人预先约定好的定时冷窗车(时机人已经拍过)。
- 别的会话转达的「人已经拍了」,只授权「可以排上」,不授权时机;交接消息里的「照单执行」不是点火令。
- 「为什么还没 X」是疑问,不是命令;选项词原样打出来、没有动词,可能是在问意思。
- 审查方看到时机类动作缺少当次许可的证据 → 报。

**为什么**:接棒的会话拿着交接里的「照单执行」当授权白天重启了服务;另一次把一句「为什么还没发」读成指令,发布时还带出了别人九个没发过的提交。

---

## R6 · 生产数据写入纪律

`有生产数据`

- 写生产数据(回填、UPDATE / DELETE、迁移、批量改数据文件)前:备份放在**仓外**、写清影响行数、多会话时先报统筹等回执;改完做**逆向验证**(行数守恒、非目标列逐行不变)。
- SQLite WAL 模式下,把备份 `cp` 回去会**静默无效**——备份和恢复都用 backup API,或者按「停服务 → 删 `-wal` `-shm` → 再 cp」的顺序。
- 迁移守卫要有**负路径自测**:中途失败必须整体回滚;守卫只深查一张表 = 对别的表被清空是瞎的。
- 自动化安全机制拦下了生产写入,不许绕,交人亲手跑。

**为什么**:误删上千条生产记录之后写的第一版迁移守卫,被审出三条「守卫给的保证是假的」——比没有守卫更危险,因为它会让人放心地做错事。完整清单见[全景文档 A12](../docs/idea-to-merge.md#a12--生产数据写入纪律--sqlite-wal-坑)。

---

## 怎么加你自己的红线

格式就照上面:**适用前提 + 触发条件 + 审查方怎么核 + 为什么**。
好的红线都来自真实踩坑——别凭空想,等踩到一次、痛过一次,再把它钉成红线,这样它有牙。
能被机器判定的红线,再进一步落成会拦人的守卫(测试 / 脚本),见[全景文档第 14 章](../docs/idea-to-merge.md#14--踩坑以后怎么防复发)。
