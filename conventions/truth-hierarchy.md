# 真值层级 + 完成层级

两套「层级」是这套工作流防「假装做完」的核心工具。

---

## 真值层级(claim 冲突时信谁)

不同来源说法打架时,**高层覆盖低层**:

1. 当前代码、目标 diff、运行时输出、命令直出结果
2. 现状文档(current-state)
3. Codex review
4. 最新 handoff
5. 更旧的 handoff
6. agent 总结

**用法**:审查方的结论必须钉在**能拿到的最高层**。低层只能当背景,不能推翻代码 / diff / 运行时 / 直接验证。
「上一份 handoff 说已经修了」**不能**盖过「现在代码里没看到这段修改」。

**为什么**:文档会漂、handoff 是历史线索不是现状事实、总结会美化。能跑命令核的就别信文档。

---

## 完成层级(「做完了」到底做到哪一层)

「做完了」不是一个状态,是**八个递进的层级**。声明只能认到有证据的那一层,缺的层级要**明说缺**,不能默认它完成:

| 层级 | 证据长什么样 |
|---|---|
| 1. 代码存在 | diff / 文件里有这段 |
| 2. 测试通过 | 测试输出 |
| 3. 已 commit | commit hash |
| 4. 已 push / 同步 | 远端有 / 同步确认 |
| 5. 已 reload / 部署 | 部署动作发生过 |
| 6. 运行时已验证 | 真跑了一次、看到预期行为 |
| 7. 用户体感已验证 | 人真用过、确认对 |
| 8. 长期观察 | 跑了一阵、没复发 |

**用法**:写汇报 / handoff / commit message 时,逐层说清。比如:

> 完成层级:代码 ✅ 测试 ✅ 已 commit ✅ / 运行时**未验** / 用户体感**未验**。

而不是一句含糊的「搞定了」。

**为什么**:最常见的事故是把第 1 层(代码写完)说成第 6 层(跑通了)。
把层级拆开,「打算做的」和「真做完的」就藏不住了。

---

## 审查方怎么用这两套

- 拿到一份汇报 / handoff,逐条问:**这句声明对应哪个完成层级?有那一层的证据吗?**
- 声明的层级 > 证据的层级 → **阻断**或**需改后通过**,把措辞改回准确层级。
- 同一个 agent 自己写声明、自己审自己 → 不算独立验证,这正是要异构对抗的原因。
