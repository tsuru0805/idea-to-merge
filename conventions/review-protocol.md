# 固定裁决格式

每一轮 review 都用**同一套固定结构**输出。固定格式的价值:你扫一眼就知道结论,不用读完全文;
做工方也知道要按哪几栏逐条回应。

> 这套格式同时写在 [`../AGENTS.md`](../AGENTS.md) 里(Codex 自动读),本文是给人看的说明版。

---

## 审查方选择

审查方不是固定的一个,按审查对象选:

| 审查对象 | 交给谁 | 为什么 |
|---|---|---|
| 纯代码 diff、设计方案、文档措辞 | 沙箱里的异构审查方(如 Codex,只读) | 不同血统,对抗性最强 |
| 涉及**运行时实况**:进程、端口、服务管理器、定时任务、真实库 | **能进真实环境**的审查者(如跑在本机的订阅内子 agent,指定强档模型) | 沙箱看不到用户级服务、连不上本地端口,会报**假阻断**,也会因此漏掉真阻断 |
| 异构审查方额度用完 | 订阅内子 agent 兜底 | 不跳审;也不为「异构」去走按量计费的裸 API |

三条配套:

- **环境不可达 ≠ 阻断。** 审查方看不到的东西,报「本环境无法验证 + 该跑哪条命令」,不报阻断(规约写在 [`AGENTS.md`](../AGENTS.md) 的 Sandbox Limits)。
- **修法回递终审。** 审查方说「建议改成 X」,做工方实现之后,终版要回递一轮——「它指了方向」≠「它审过实现」。
- **收工文档也审。** handoff、看板改动、工单登记段整批递审,没有「纯文档低风险」的免审例外。

调用 Codex 的形态:单独一条、前台跑、末尾加 `< /dev/null`;默认模型被拒用 `-m` 指定;管道喂 diff 的写法不用改。详见 [setup](../docs/setup.md#3-非交互调用codex-exec)。

---

## 三档裁决(只能选一个)

| 裁决 | 含义 | 之后做什么 |
|---|---|---|
| **通过** | 声明和证据对得上,没有阻断项 | 可以进记录 / 合并 |
| **需改后通过** | 改本身可接受,但**措辞或验证层级**要先修正 | 按裁决改,再审 |
| **阻断** | 照现在这样会写出错误或不安全的记录 | 必须改,再审 |

---

## 输出七栏

```markdown
## 裁决:通过 / 需改后通过 / 阻断

## 最关键的一条
<最该让人知道的一件事,一句话>

## 阻断项
<只列真正挡住验收的问题,每条带 文件:行号 + 证据>

## 可放行项
<有证据支撑、可以进记录的改动>

## 验证层级修正
<把吹过头的「已完成」改写成准确的层级>

## 下一步最小动作
<让这个 packet 能被接受的最小一步>

## 本轮命令清单
<这次 review 跑过的只读命令>
```

---

## 为什么要「本轮命令清单」

让审查方**亮出它看了什么**。一份没有命令清单的裁决,你没法判断它到底核了还是拍脑袋。
`git diff` / `rg xxx` / `cat path:line` 列出来,裁决才可追溯——审查方自己也不容易「轻描淡写」。

---

## 做工方怎么回应裁决

- **逐栏回应**,别整体说「改好了」。哪条阻断项怎么修的,对应写。
- **核查、不无脑同意**。觉得审查方判断有误,就摆证据二审 / 反驳——目的是把工程推对。
- 采纳的修法实现后,**终版回递终审**;驳回的要给证据(生产实测 > 推演)。
- 回合收敛:一审 → 修 → 二审确认是常态;第三轮只留给「驳回了阻断项」这类必须闭环的场合。来回几轮不收敛,交给人。
- 收敛后,把结论**写进 commit message**(`codex 回执:…`),不另存报告文件。
