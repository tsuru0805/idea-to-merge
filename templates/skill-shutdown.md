# 收工 Checklist Skill 骨架

> 拷进你项目的 `.claude/skills/shutdown-checklist/SKILL.md`,按你项目填。
> 收尾是 AI 最容易「总落下这个那个」的环节——这份 checklist 就是对治。
> 关键设计:**触发词写进 description**(人说「收工」就自动走)+ **交接前也强制触发**
> (没走完 checklist 的交接 = 没交接,下一棒拿到的是一地散件)。
> 流程图见[图 ⑥](../docs/flowcharts.md);每一步为什么存在,见[全景文档第 7.3 节](../docs/idea-to-merge.md#73-收工-checklist)。
> 用不到的步骤(比如没有部署环节就删第 0.5 步、没有服务表就删第 4 步)整条删掉。

---

```markdown
---
name: shutdown-checklist
description: 每日收工流程。当维护者说"收工""今天到这""结束""下班"或任何表示
  当天工作结束的话时触发;**任何交接/传棒/handoff 前也必须触发**(交接=先收工,
  不许光扔一份 handoff 就走)。触发后严格逐条执行,不准偷懒不准跳步。
---

# 收工 checklist(喊"收工"或任何交接前必做)

> 每条都要过,过不了的明说为什么。

0. **范围守恒自查**(与守卫同级的硬规):今天是否把维护者拍过的任何范围**切小/推迟/
   转「欠账/二期/等拍」**了?逐单过一遍。有 → 收工总结**显性点名+原因**;只有物理
   原因合法(等部署窗口/外部依赖/等人在场),「工作量大/先做核心」不合法。静默切小=违规。

0.5 **装载守恒自查**(有部署的项目):
   - 今天有没有产生**候车货**(合了主干、要等部署才生效的改动、要重启才生效的配置)?
     有 → 下一班车必须**已挂**,按**确切的任务名**两处核:<任务定义文件存在> +
     <服务管理器里已加载>。旧日期的残件双绿不算数。挂不了 → 收工总结写
     「下一班无车,货 X 顺延,原因 Y」。不存在什么「常规机制」——写了「候车」就要有车。
   - 拆当日跑完的旧车时,同一动作里核对还有没有候车货;有货没新车=不许拆完就走。
   - 今天写进任何文档的「已装载/已生效」按层给实据:**已装载**=进程层(启动时刻=发车
     时刻)+代码层(逐仓 HEAD==钉货);**已生效**=再加产出层(生产真输出)。不够就改写
     成「候装载/候验证」或当场补验。多仓件只装了一仓=没装载。

1. **handoff-YYYY-MM-DD.md** 新建今天的交接条:时间线 + 决策点 + 范围守恒 + 完成层级 +
   装载守恒 + 踩坑 + **验收区两栏**(AI 已自核附证据 / 留给人的体感项)+ 在途棒(说人话)+
   未完成项与超期件。多棒同日各自收工时,文件名加主题后缀防撞。

2. **todo 看板**按规约维护,四个动作:
   - **改**:推进过的单,看板行**整条重写**为当前态(新态替换旧态,禁划线/日期链);
   - **关**:完成的移「已完结」表一行;
   - **钉**:自己的在途挂牌行收工即删;临时行逐条核对删除条件;
     欠账做完**删行**,拖龄超 <3> 天的收工总结里逐条点名;
   - **量**:跑看板守卫,**硬失败项(trail 条目/删除线/超长行/指针链超限/分区识别失败)
     任一 > 0 = 当场修完再往下走**。
     ⚠ 在 worktree 里跑必须用 <GUARD_REPO 之类的环境变量> 指向 worktree,否则读的是主仓旧文件=假绿。
     ⚠ 用脚本批改看板:先按分区标题切出范围,只在该段内找行,`assert len(hits) == 1`;
       脚本任一步失败,后面的 add/commit/push 不许照跑(别用 `;` 串)。

3. **工单文件**:当天推进过的,状态/步骤当场更新(工单状态的权威在工单文件,看板只留一行)。

4. **服务表**:新增/搬家/下线/端口变 → 更新权威总览 + 对应服务文件。
   <没有服务表的项目删掉本条;有的话:新增服务两件套缺一不算完成>

5. **架构文档**:结构/数据流/命名约定变了才更新对应区块;不写流水账,写当前结构。

6. **memory**:今天沉淀的教训写成 feedback 条目(是什么+为什么+下次怎么做+权威在哪);
   **改 memory 文件必须同步改索引行**——不进索引的 memory 等于没写。

7. **收工文档整批递审**:当日 handoff + 看板改动 + 工单登记段一起交给审查方。
   审查要点:事实性(提交号/班次/数字自洽,不夸大)+ 防漂(权威源唯一,看板行合规约)
   + 口径(模拟器验收≠人验收,主嫌≠定案,候选≠根治)。回执核查不盲从。
   **「纯文档低风险」不是免审理由——没有免审例外。**

8. 审过之后,仓内改动 **commit + push**(走 PR 的项目含合并;**有自动部署(合并即上线)的项目,这一步只
   push 分支、不合并**,合并走全景文档 7.1 第三档:登记货单 → 当次许可 → 守卫 → 合并)——只提交本棒范围内的改动(先 `git status -s` 核清单,
   别把别棒的 WIP 一起收走);push 失败不硬解,汇报现场。

9. 给维护者一条**收工总结**:今天做了什么 / 待验收什么(只列体感项)/ 第 0 步点名的项 /
   第 0.5 步的车况 / 看板守卫输出 / 明天从哪接。

## 月度归档巡检(每月初一次,非每日)

10. handoff 活区只留当月,更早的移进归档区(进去即冻结,只查不改);
    已完结工单随巡检归档。**归档前先 grep 代码里有没有脚本在读该文件**
    ——工单完结 ≠ 文件可挪,断粮事故就是这么来的。
    顺手对一遍 memory 索引与实际文件;对服务表做一次只读对账(缺失/多余/状态不一致),
    异常另开工单,不自动改。
```
