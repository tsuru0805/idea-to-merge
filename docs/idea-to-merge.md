# idea-to-merge · 从一个想法到合并上线

> 这是进阶手册:一个想法从提出到合并、部署、验收、关单,每一步该守的规矩。内容来自一个 24/7 跑在 Mac mini 上、常年多 session 并行开发的个人系统,每条规矩背后都是一次真实翻车。
>
> 规则标签怎么看、文中的日常用词、整条线的全景图,都在[参考页](reference.md);第一次用 Claude Code,先看[新手入门](beginner.md)。

# Ⅰ · 一个想法的一生

## 1 · 两权分立:需求判断权在人,成本估算权在 AI

一切流程的最上游,是一条**分权规矩**:

> **痛不痛、要不要做,人说了算;要动什么、花多少,AI 说了算。两权不混。**

具体说:

- 你提需求时,[CC](reference.md#cc) **可以**说:「这要动 X、改 Y、预计 N 小时」「会影响 Z 模块,要一起调」——这是它的专业判断,该说,说清楚是义务。
- 但 CC **不准**说:「我觉得这个点没那么痛」「不一定要改」「没必要」——痛不痛只有用的人知道。AI 对你的生活没有发言权,它只对代码的成本有发言权。
- 你听完成本,仍然要做,那就做。**不许再劝退第二次。**

**为什么值得钉成规矩**:这是人和 AI 结对里最常见、也最消耗感情的摩擦——你说想要个东西,AI 先给你泼三盆冷水。分权之后,对话里只剩事实:它报价,你[拍板](reference.md#拍板)。讨论会变得非常快。

反过来这条也保护 AI 侧:它给出的成本估算你要当真。它说「这个改动会牵连三个模块」,那就是会牵连三个模块,不要用「应该没那么复杂吧」去砍它的工程判断。

**两条后来补上的配套**(全文在规则库):

- **成本话语权有时效。** 立案之前,成本影响范围;**立案之后,成本只是信息**——超预估了就报给人重新拍,AI 不许自己把已拍的范围切小,更不许拿账劝退。见 [A1 完整交付律](#a1--完整交付律)。
- **动手前先复述。** 人说完需求,AI 逐条复述「你要的是 1/2/3」,标明方案覆盖哪条、不覆盖哪条及原因,人确认了才动。省略必须摆在人眼前由人裁,不许静默剪裁。见 [A2 需求复述闸](#a2--需求复述闸)。

## 2 · 节奏约束:两个极端都要钉死

AI 干活的节奏有两个典型失控方向,**而且互为反弹**——你只修一边,它必然弹向另一边。

### 失败模式 A · 推诿拆天

症状:明明一天能做完的活,被拆成「今天做一半,剩下明天」。尾巴过夜,第二天上下文冷了、优先级变了,尾巴就烂在那里。

对治规矩:

- **不需要观察的活,当天做完,禁止拆天。**
- 跨天只认**物理原因**:等部署窗口、等外部依赖、等人在场——且必须**提前报备**,不是拖到晚上补一句「明天继续」。「工作量大」不是理由,工作量大就拆成并行的[棒](reference.md#棒),不是拆成几天(和 [A1 完整交付律](#a1--完整交付律)同一口径)。
- 观察期只用来验证已经做完的东西,**不能当作「暂缓做下一件」的理由**。

### 失败模式 B · 闷头狂奔

症状:领了个活,一口气跑一个半小时、烧几十万 token、中间零汇报。方向要是错了,就是全损——钱和时间一起。

对治规矩:

- **大活分段汇报**:每完成一个可验证的段落,停下来报一次,人确认方向再走下一段。
- **人催快 = 砍范围,不是加倍跑。** 这条反直觉但极重要:着急的时候正确动作是缩小交付,而不是更疯地烧。
- **动手前先写验收清单**(哪些测试要绿、哪些行为要证),测试的终点 = 清单全绿,**绿了就停**。清单之外「可能还要测测这个」= 上头信号,出现即停。
- **同一个失败连修两轮不绿 → 停下汇报**,带现场(失败输出 + 两次尝试),不许无限迭代。

### 方法论:约束要成对写

我们家真实走过这条弯路:先是嫌它拖,加了一条「别拖延」的约束——它立刻滑向另一个极端,一做东西就停不下来。

调 AI 的行为像调控制器:**单边约束必然过冲**。「别拖延」和「别乱跑」必须同时写,两端都钉死,中间留出来的才是正确行为区间。你在给自己的 AI 立规矩时,凡是节奏类的,都检查一下有没有只写了一边。

## 3 · 工单系统:原话、编号、参照

想法过了两权对话,第一站是**立工单**——一个 markdown 文件,格式见[工单模板](../templates/ticket.md)。除了互审流程需要的 spec(改什么/不改什么/怎么验),我们家的工单还有三样东西,都是被真实需求逼出来的。

### 3.1 原话区:人的原话,一字不改

工单的**第一个区块**永远是提需求的人的**原话**——微信里怎么说的、嘴里怎么念叨的,原样抄进去,不润色、不概括。AI 的转译(规范化的 spec)写在下面,**转译永远不许覆盖原话**。

为什么:转译必然丢意图。做着做着跑偏了、或者两周后回头看「当初到底要什么」,唯一可靠的锚就是原话。验收时对照的也是原话,不是 AI 自己写的验收标准——不然就是它自己出题自己判卷。

这是我们家坚持得最好的一条,强烈推荐。成本几乎为零,救回来的次数两只手数不完。

### 3.2 全局唯一编号 + 占号防撞

工单文件名带**全局唯一递增编号**(`工单_NN_短名.md`)。单人单线时这只是整洁;**多 session 并行时,编号就是锁**:

- 建号前先 `git fetch` 主干,看当前最大号;
- 建号后**立刻在看板登记一行、commit 推上主干——上了主干才算占到号**。

这条规矩来自一次真实三连撞:三个并行 session 同一天各自建单,撞出重号,事后合并对账很痛。「推上主干才算占号」之后再没撞过——git 天然是这个锁的仲裁者。

### 3.3 参照与关联区:溯源链

工单里固定留一个**参照与关联**区:

- **外部参照**:这单参考了哪个开源仓 / 教程 / 帖子——一行一条,链接 + license(若抄了代码)+ 用在哪。
- **关联工单**:和哪几单有依赖或渊源,编号互链。

为什么:「先搜再造」(第 5 章)搜来的东西,不落纸面就只存在于那一个 session 的脑子里。半年后回头看「当时为什么选这个方案、抄的谁」,顺着参照区就能摸到源头;新接手的棒也不用考古。**知识要有出处,关系要显式**——这和第 12 章的防烂原则是同一个精神。

### 3.4 每个改动项自带「验证命令 + 通过判据」

工单的改动清单不是一列文件名,而是一张表:**改什么 / 验证命令 / 通过判据**。验证命令是一条能直接复制跑的命令(一条测试、一条 SQL、一次 grep、一次接口调用),通过判据是「看到什么算过」。

为什么:没有判据的改动项,验收时只能靠「我觉得好了」;而判据写在立案时,就是在动手前把「做完」定义清楚——它同时是自审的终点、[审查方](reference.md#审查方)的标尺、部署后三层验证(第 7.1 节)的产出层判据。我们家吃过亏:部署清单上的一件货没写判据,装上去后它「无害降级」安静空转了三天,所有机器检查都是绿的。

### 3.5 「空窗防护」一行

`有部署` `有生产数据` 已经确诊的生产问题,修复如果要等部署窗口(第 7.1 节)才能生效,工单里必须写一行**空窗防护**,三选一:

1. **防护措施**:数据止血 / 临时降级 / 看护脚本,外加重跑节奏(比如「每晚止血一次,直到装上」);
2. **明写「防不了」+ 预计影响**(「预计每天 N 次失败」),交给人拍:忍到窗口,还是破例提前发;
3. **当场装上**(人拍了破例时)。

没有这一行 = 不合格工单,审查方按阻断提。全文见 [A8 修复空窗防护](#a8--修复空窗防护)。

## 4 · worktree 纪律:主干永远干净

git 层面一条铁律:

> **每一棒干活都在自己的 worktree 里,开独立分支;主 checkout 永远保持干净,只承担一个职责——[部署位](reference.md#部署位)。**

- 开工:`git worktree add ../<repo>.worktrees/<棒名> -b <棒名>`,所有改动、所有 commit 都发生在 worktree 里。
- 收工:审过之后 rebase 主干、回主 checkout `merge --ff-only`、删 worktree。主 checkout 上只发生 ff 合并和部署动作,**永远不在它上面直接编辑**。
- git 写操作一律 `git -C <worktree路径>`,不 `cd` 进仓根再跑——cd 状态是隐形的,`-C` 每条命令自带路径,错不了。
- 也可以让 Claude Code 替你建:**CLI** 用 `claude -w <名字>`(`--worktree`),默认建在仓根的 `.claude/worktrees/<名字>/`、新分支名 `worktree-<名字>`;**桌面版**新建会话时在分支名旁边勾选 worktree 选项(默认位置相同,可在设置里改)。(按官方文档核过。)

**一个大多数人想不到的坑:跑测试也算破坏性动作。** 我们家真实规矩是「主 checkout 永不跑全量测试」——因为有些代码的状态文件路径是按**模块位置**定位的(`Path(__file__).parent / "data"`),和 cwd 无关,你在哪个目录跑都写的是主 checkout 里的**生产数据**。worktree 里没有那份数据,天然免疫。如果你的项目主 checkout 同时是运行时,这条直接抄走。

但也别以为进了 worktree 就万事大吉——**worktree 隔离的是 git,不隔离环境变量**。最常见的漏法是 `.env`:很多库的「无参加载 .env」会从当前目录**一路向上找**,而 worktree 往往就嵌在主仓目录底下,于是测试进程吸进了主仓的生产配置,真的去调了生产服务。光靠纪律防不住,要落成测试套件里会报红的[绊线](reference.md#写口绊线),见 [A6 测试写入绊线](#a6--测试写入绊线--dotenv-爬出-worktree)。

**接手必读顺序**也钉死(新 session 开工第一件事,顺序不许乱):

1. 项目说明(CLAUDE.md,自动加载)——红线和协作规范;
2. 服务总览(哪些东西在跑、端口、职责的权威表);
3. todo 看板——现在有什么单、什么状态;
4. 最近 1-2 份 handoff——上一棒做到哪、踩了什么坑;
5. 要接的那个工单文件本体。

读完这五样,一个全新的 session 就有了全局。这个顺序本身就是防漂设计:先读权威源,再读历史线索(handoff 排在 todo 之后,因为它是[真值层级](../conventions/truth-hierarchy.md)里更低的一层)。

## 5 · 方案 → 代码 → 互审

### 先搜再造

从零做一个功能,第一动作不是写码,是**广搜现有方案**:开源库、教程、别人的实现。别重复造轮子,也别对自己的智商过于自信。搜来的东西审慎判断、不盲从,同时正面想「有没有更优雅简便的路」。搜到什么、用了什么,**落进工单的参照区**(第 3.3 节)。

一个例外要想清楚:**管道可以抄,灵魂不外包。** 每个项目都有几个「它之所以是它」的核心文件(对我们家是几份核心 prompt)。基础设施尽管抄开源,那几个文件永远自己写——外包了它们,项目就不是你的项目了。

### 死胡同协议

卡死的时候(同一个问题绕了三圈没进展),两条出路,别硬撑:

1. **查一手资料**——注意是一手:官方文档、源码、跑命令直接验。二手结论(教程、论坛贴、甚至代码注释)都可能过期。我们家吃过一次大亏:一整份调研的六条结论全被推翻,起因就是引用了仓库里过期的注释当事实。
2. **拉另一个模型交叉讨论**——把「我们卡在哪、两边的论点」整理成一段,丢给一个不同血统的模型掰扯。它没有你们绕了三圈的思维定势,经常一眼看到墙上的门。

### 互审

设计和代码各过一轮异构互审,循环到放行——完整流程就是[七步循环](workflow.md),不重复讲。几个补充:

- **审查方不一定非是 Codex。** 同一订阅内跨档互审(旗舰做工、派另一档[子 agent](reference.md#子-agent) 当审查员)也成立——不产生新增账单,占的是包月额度(见第 11 章);损失一点「异构血统」的对抗性,换来低成本低摩擦。我们家的用法:大改动上 Codex(异构对抗最狠),日常小审用订阅内子 agent。
- **按审查对象选审查方。** 纯代码 diff 交给沙箱里的异构审查方最好;但审查对象一旦涉及**运行时实况**(进程在不在、端口通不通、服务管理器里挂了什么、定时任务、真实库),就必须交给**能进真实环境**的审查者(比如跑在你机器上的订阅内子 agent)。沙箱审查方看不见你的用户级服务、连不上本地端口,会报一串**假阻断**——更糟的是,它会因此漏掉真阻断。全文见 [A7 审查方选择与兜底](#a7--审查方选择与兜底)。
- **额度用完不停审。** 异构审查方额度耗尽时,用订阅内的子 agent(指定强档模型)兜底;不许以「审查方没额度」为由跳过审查。
- **建议了方向 ≠ 审过实现。** 审查方说「建议改成 X」,你照做之后,**终版实现它还没见过**——必须回递终审一轮才算[收口](reference.md#收口)。只自测就合并,等于审查环在最后一步断了。
- **调用形态有讲究。** `codex exec "<prompt>"` 一律**单独一条、前台跑、末尾加 `< /dev/null`**;本机默认模型被服务端拒了就用 `-m <模型名>` 指定。管道喂 diff 的写法(`git diff | codex exec ...`)不用改。原因见 [setup 第 3 节](setup.md#3-非交互调用codex-exec)。
- **现在有官方插件了。** OpenAI 官方出了 [codex-plugin-cc](https://github.com/openai/codex-plugin-cc)(2026 年 3 月发布):在 Claude Code 里直接调 Codex 做 review 和任务委托,计费走 ChatGPT 订阅或 API key,用量计入 Codex 侧限额。和本仓手搓的 `codex exec` 是同一精神,集成更顺滑;手搓版的价值在于你能完全控制审查规约(AGENTS.md 那套)。两条路都通,按口味选。

## 6 · 红线:怎么让 AI「停下来问你」

用过 CC 的人都会好奇一件事:为什么它有时候会在合并、部署、删东西之前**自己停下来**等人点头?这不是玄学,是两层闸,各管一摊:

### 硬闸:harness 的权限系统

Claude Code 的 settings 里可以配 permissions,规则分三档:**allow**(免批直跑)、**ask**(弹窗要人按一下)、**deny**(直接拦)。默认模式下,除了一组内置的只读命令,没命中 allow 的 Bash 命令都会弹窗问你。这层**由 Claude Code 执行,不由模型决定**——写在 prompt 或 CLAUDE.md 里的话改变不了它放行什么,适合钉「通用危险动作」:删文件、改系统配置、发布类命令。

但要知道它的边界:Bash 规则是**按命令字符串匹配**的,同一个动作换个写法(换参数顺序、用绝对路径调同一个程序、包进 `sh -c`)就可能匹配不上,官方文档自己也说约束参数的 Bash 规则是脆弱的。真要硬拦,配 **PreToolUse hook**(在命令执行前用你自己的逻辑检查完整命令文本,能直接拒绝),或者开 **sandbox**(文件系统和网络层面的隔离,不依赖命令文本)。

### 软闸:写在必读文件里的纪律

「合并前先请示」「花钱先申请」「破坏性命令三确认」这些**不在 settings 里**——它们写在项目说明(CLAUDE.md)和 memory 里,靠模型自觉遵守。听起来不可靠?它能稳,靠三件事:

1. **写在必读位置**——项目说明每个 session 自动加载,不存在「没看到」;
2. **写得足够具体**——不是「要小心生产数据」,而是「路径含 `data/`、`db`、`vault` 任何一个,先停下问人」。模糊的规矩没有执行力,具体到能机械判断的规矩才有;
3. **违反必沉淀**——每次翻车,复盘写成一条新 memory(见第 13 章),下个 session 自动带着这条教训开工。规矩是活的,越用越密。

### 为什么两层都要

硬闸(权限规则)只认命令字符串,表达不了语境——「合并」本身不危险,「没请示的合并」才危险,这种判断只有软闸写得出来。所以配比是:**硬闸管通用危险命令,业务红线(合并、部署、花钱)靠软闸。**

软闸的具体条款,[通用红线](../conventions/redlines.md)里那三条(隔离分支 / 破坏性命令三确认 / 反轻描淡写)几乎人人适用,直接抄。再强调一句那边说过的:**好红线全部来自真实踩坑**。我们家最痛的一次:一条「先测一下」的随手命令,在错误的目录里清掉了生产库 1556 条数据——三确认协议就是那天晚上立的。别凭空想红线,痛过一次再钉,钉下去才有牙。

## 7 · 发车、验收、收工

### 7.1 合并 ≠ 部署:按部署成本选窗口

先约定几个词:我们家把一次部署叫**[发车](reference.md#发车货单候车货)**(一趟「班车」),合了主干、等着被部署的改动叫**[候车货](reference.md#发车货单候车货)**,登记它们的清单叫**[货单](reference.md#发车货单候车货)**,定时自动跑的那次部署任务叫**车**。

`有部署` 代码过了**[节点②](reference.md#三个人类节点)收工批准**、合并进主干后,怎么「装上去」?我们家走过一段弯路才想明白:**发车窗口不是一条固定规矩,而是由「这次部署的代价」决定的。** 先回答一个问题——**重启 / 热更新 / 迁移这一下,会让什么失效?**

| 部署代价 | 发车窗口 | 授权 |
|---|---|---|
| **贵**:重启会让昂贵的状态失效(LLM 的 prompt 缓存、长连接上的在途请求、预热数据) | **[冷窗](reference.md#冷窗静默窗)**:低峰期的定时窗口。改动先登记进「货单」攒批,蹭那一轮本来就会发生的冷启动 | 冷窗这个**时机是人预先约定过的**,货单经人拍过、上了车,定时车到点就发;**白天临时提前发,只认人当场的字面许可** |
| **低**:重启几乎不损失什么 | **任意[静默窗](reference.md#冷窗静默窗)**都可以发([守卫](reference.md#守卫)确认零在途流量,见 A4) | **每一次都要人当次点头**,许可不留存——「上次说过可以」不算这一次 |
| **有自动部署**:合并即上线(CI 自动发布,或主 checkout 本身就是运行目录) | **合并本身就是发车** | 合并前就要备齐发车所需的一切,顺序是:登记货单 → 人的当次许可 → 守卫放行 → 合并 |

几点展开:

- **冷窗为什么值钱。** 我们家早期的服务是 24/7 长跑的 LLM 应用,吃 prompt cache 吃得很重——重启一次,整条缓存冷掉,下一轮全量重写;cache 写入价是读取价的 **12.5–20 倍**(按缓存 TTL 档位)。白天随手一个「小重启」就是一笔真实开销,而凌晨反正有一次计划内冷启动,蹭那一班车,**边际成本 ≈ 0**。
- **代价变了,窗口跟着变——但授权不放松。** 后来这些服务换了计费方式,重启不再产生缓存账,我们就把「只许冷窗」放宽成「任意静默窗」。**放宽的是窗口,不是授权**:不在预约的冷窗里发,每一次都要人当次点头。这条规则还写成了**条件式**——一旦服务切回按量计费,冷窗纪律自动全额恢复,不需要谁记得改回来。
- **「只是合并一下」是自动部署项目最常见的错觉。** 如果主 checkout 就是运行目录、或者 CI 会把主干自动发出去,那么「合并」和「发车」是同一个动作。我们家有几个仓的主 checkout 就是运行目录,往那里合并 ≈ [装载](reference.md#装载),所以只有统筹的那个 session 才能往部署位合入(见 [A13](#a13--总调度多-session-打法增补))。
- **不管哪一档都不变的四样:**
  1. **货单**——每件货登记时就写明「验证命令 + 通过判据」(第 3.4 节),发车后照单验;
  2. **守卫和动作同一条命令**——查在途流量与重启、断言 HEAD 与发布,绑在一条 shell 命令里([A4](#a4--检查和动作绑同一条命令));
  3. **交接棒不是点火令**——交接消息里写着「照单执行 / 可以发」不等于人现在许可了。我们家踩过:一个接棒 session 拿着交接里的「照单执行」当授权,白天重启了服务,砸掉整条热缓存;
  4. **装载三层验证**——进程层、代码层、产出层三层实据齐了才叫「已装载 / 已生效」([A3](#a3--装载三层验证--收工装载守恒))。

就算你的项目没有缓存问题,「货单 + 窗口 + 当次授权」也值得抄:部署动作可预期、变更天然合批、而且每一次上线都有人知情。

### 7.2 验收:功能由 AI 自己证明,人只验体感

部署完 ≠ 做完。但「验收」这件事里,人和 AI 的分工要分清:

- **功能验收归 AI。** 功能对不对、有没有生效,AI 自己拿证据证明:模拟器 / 真浏览器里跑一遍并截图、看服务日志、查库里有没有那行、调一次接口看返回。证据贴进汇报,而不是写「请你去试一下」。
- **人只验 AI 验不了的。** 体感(快不快、顺不顺)、审美(像不像、丑不丑)、对不对味——这部分只有用的人能判。给人的验收项压到最少,每项**傻瓜级**:打开哪、看哪、一步操作。
- **只能靠自然使用才出现的产出,用「静默窗自核」。** 有些产出只有在真实使用中才会出现,别为了验收让人专门去触发一次——等它自然发生一次,AI 再去查日志和库。

为什么:让人去「点一下看看出没出来」,等于把人当测试机,把人的使用时间变成 AI 的验收步骤。同一个问题让人陪着试三遍,是最伤信任的事(见 [A11](#a11--同一-bug-二报即停))。

三个动作把验收闭上:

1. **handoff 里验收区分两栏**(见[模板](../templates/handoff.md)):「AI 自核」(已验的附证据;只能等自然使用才出现的,写明静默窗自核计划)和「留给人的体感项」。后者每项写清「验什么 + 怎么验 + 一步操作」。
2. **看板上待验项挂牌**,验过即删。不验,它就一直在你眼前。
3. **下一棒开工的固定动作:先追昨日验收,再领新活。**

### 7.3 收工 checklist

「收工」是个触发词——人说出口,CC 走一遍固定 checklist,不准跳步(骨架见 [收工 checklist 模板](../templates/skill-shutdown.md),流程图见 [图 ⑥](flowcharts.md)):

- **第 0 步** · **范围守恒自查**:今天有没有把人拍过的任何范围**切小、推迟、转成「二期 / 欠账 / 等拍」**?有就在收工总结里**显性点名 + 原因**——只有物理原因(等部署窗口、外部依赖、等人在场)算合法,「工作量大 / 先做核心」不算。静默切小 = 违规。([A1](#a1--完整交付律))
- **第 0.5 步** · **装载守恒自查**:今天有没有产生「候车货」(合了主干但要等部署才生效的改动)?有 → 下一班车**确实挂上了**(按确切的任务名核,不是「应该有」);挂不上就在总结里写「下一班无车,货 X 顺延,原因 Y」。今天写进文档的「已装载 / 已生效」逐条对照三层实据,不够就改写成「候装载 / 候验证」。([A3](#a3--装载三层验证--收工装载守恒))
- **第 1 步** · 写今天的 **handoff**(时间线 + 决策点 + 踩坑 + 验收区两栏 + 未完成项 + 在途棒说人话);
- **第 2 步** · 刷 **todo 看板**(按第 12 章的规约改 / 关 / 钉 / 量),**跑看板守卫,硬失败项清零才往下走**;
- **第 3 步** · 推进过的**工单文件**状态更新;
- **第 4 步** · **服务表**同步(今天新增 / 搬家 / 下线了什么);
- **第 5 步** · **架构文档**同步(结构变了才动,没变不动);
- **第 6 步** · **memory** 同步(今天沉淀了什么教训;改 memory 文件同步改索引行);
- **第 7 步** · **收工文档整批递审**:handoff、看板改动、工单登记段一起交给审查方,审事实性(提交号 / 数字自洽、不夸大)、防漂(权威源唯一)、口径(模拟器验收 ≠ 人验收、主嫌 ≠ 定案、候选 ≠ 根治)。**没有免审例外**——「纯文档低风险」不是理由;
- **第 8 步** · 审过之后,仓内改动 **commit + push**(走 PR 的项目,这一步也包括合并;有自动部署(合并即上线)的项目,这一步只 push 分支、不合并,合并走第 7.1 节第三档);
- **第 9 步** · 给人一条**收工总结**:今天做了什么 / 待验收什么 / 第 0 条点名的项 / 明天从哪接。

第 7 步是我们家后补的:有一天代码面审了两轮,收工文档自认「纯文档低风险」直接合了,结果 handoff 里把「打算修」写成了「已修」。后来把「收工文档递审」**焊进 checklist 本体**,走单即触发,不再靠记性。

一条铁律:**交接 = 先收工。** 要把活交给下一棒,必须先走完这套——handoff 只是第 1 步,不是全部。没走完 checklist 的交接 = 没交接,下一棒拿到的是一地散件。

# Ⅱ · 规模化运行:多棒并行

单棒走完上面的主线,小系统就够用了。当多个工单开始并行、多个 session 同时在跑,才需要这一部——组织怎么搭、额度怎么花。

## 8 · Skill 体系:把打法钉进文件,不靠每场重教

Claude Code 的 skill 机制:`.claude/skills/<name>/SKILL.md`,frontmatter 里写一段 description——**description 就是触发器**,描述里写清「什么时候用我」,匹配场景时 CC 自动加载全文。你不用每个 session 重新教一遍规矩,规矩自己长在仓库里。

我们家五个 skill,分两层 + 三个场景件:

### 底层:打法手册(所有 session 的第一站)

**任何** session 接手干活,第一站先读它——不管这棒是[总调度](reference.md#执行棒总调度)还是[执行棒](reference.md#执行棒总调度)。内容是「怎么干活」的全部纪律:接棒第一动作、工单生命周期每一步的规矩、跟人说话的格式、额度纪律。

它开头有一句定位,是整个体系的魂:

> 模型会换,工程师不换——读完这份,你就是那个工程师。

以及一条铁律:**skill 教打法,不教工程事实。** 手册里永远不写「现在有哪些服务、什么状态」这类快照——那些必然过期,一律链接到权威源让它自己查。手册只写不会过期的东西:纪律、顺序、格式、教训。

### 叠加:总调度打法(只有总调度棒读)

多工单统筹的那个 session 才触发:盘点、[纠漂](reference.md#纠漂)、派棒模板、验收环、对人汇报的格式(详见第 9 章)。执行棒不读它——执行棒不需要知道怎么派活,读了反而容易越权。

### 场景件三个

- **决策侧写**:[维护者](reference.md#人维护者)本人的工程决策偏好档案——什么时候要稳、什么时候要快、对哪类方案天然反感、说「先搞起来」时真实含义是什么。CC 在架构讨论、技术选型前查它,给出的选项就不会牛头不对马嘴。这相当于把「和这个人共事三个月才摸清的脾气」写成文件,每个新 session 出生即知。
- **设计规范**:动任何 UI/排版前必读的审美语言(什么风格算好、红线配色、禁忌)。设计审美是最难口头传递的东西,钉成文件后「做出来不像」的返工少了一个量级。
- **收工 checklist**:触发词是「收工」——听到就逐条执行一套固定动作,不准跳步(内容见第 7 章)。收尾恰恰是 AI 最容易「总落下这个那个」的环节,checklist 是对治。

两个骨架可直接抄走改用:[总调度骨架](../templates/skill-dispatcher.md) / [收工 checklist 骨架](../templates/skill-shutdown.md)(都是**骨架**——结构和纪律给全了,占位符按你项目填)。打法手册没有单独骨架——上面的描述加这两个骨架,足以拼出你自己的版本。

## 9 · 单干 vs 总调度:两种运行模式

### 单干模式

只有一个工单在做:一个 session 从想法陪到收工,走完第Ⅰ部的全程。小系统、单线任务,这就够了,别上总调度——多余的层级是纯开销。

### 总调度模式

多个工单要并行时,结构变成:**一个总调度棒长驻 + N 个执行棒**。人开好这些 session,想法只进总调度;执行棒对总调度汇报,总调度对人汇报。目标是:**人只在拍板点出现,搬话的活全部消灭。**

总调度的核心纪律,每条都是真实翻车换来的:

**接棒第一动作 = 汇报,不是干活。** 接手总调度后只做只读核查(fetch 主干、读工单、核运行时),核完先汇报「现状对齐了什么、发现哪些偏差、打算怎么排」,**人拍了才开工**。反例:某次接棒的 CC 拿着交接 prompt 闷头干完一整棒才露面——还抢了一个在途执行棒正在做的活,白干一场,险些撞车。另一半规矩:**你服务的对象是现在的人,不是上一棒**——交接 prompt 是上一棒的遗言,它和人现场说的任何一句冲突,以人为准。

**派单前先纠漂。** 看板说「待做」≠ 真待做。派单前先 `git log --grep` + 查运行时,核一遍这活是不是其实已经做完了。我们家有过一天撞出四起漂的记录(功能已上线一周、[台账](reference.md#欠账台账拖龄)还写待做,照字面派单就是重复劳动)。判据永远是[真值层级](../conventions/truth-hierarchy.md):**代码/运行时 > 现状文档 > handoff**。

**派单模板,缺一不可**:工单号 / 目标一句话 / 必读权威文件 / 当前真实状态(纠漂后的) / 允许改的范围 / **禁止碰的范围** / 逐项可验的验收标准 / 停止条件 / **预计时长**(超时 = 停下报,不许继续耗) / 返回格式。末尾必加一句:「**全部自己动手,不许再派子 agent**」(理由见第 10 章)。

**验收环,每棒回报走一遍**:① 总调度亲手复测——测试数字自己跑出来,不信执行棒的转述;② diff 范围核——越界就返工;③ 递审查方过一轮互审;④ **返工打回原棒**(它上下文还热,重开新棒等于重付一遍装载费),返工消息带具体条目和代码位置,不许说「再检查一下」这种没法执行的话。

**对人只报拍板题。** 人只拍五类:要不要 / 往哪走 / 像不像 / 花不花钱 / 碰没碰红线。排期、工序、派棒时机是总调度自己的职责,**直接定 + 告知**,不许抛回给人——给人的消息里出现「你看什么时候做?」就是失职信号。

### 跨 session 的规矩

- 动共享文件前先向其他在途 session 打招呼认领;**发消息 ≠ 认领成功,收到回执确认无撞才动手**——消息可能根本没被读到。
- **session 之间怎么发消息**(按官方文档核过,版本更新后以官方为准):
  - **CLI**:Claude Code v2.1.224 起(macOS / Linux / WSL 2;Windows 原生 v2.1.234 起),同一台电脑上的 session 之间可以直接发消息,默认开启;Claude 用 `ListAgents` 找对象、`SendMessage` 发送。用 `@会话名` 指定对象要 v2.1.232 起;经第三方云平台接入、或关了功能开关拉取的,同机发消息要 v2.1.248 起。输入 `/list-agents`(`/peers`)可检查功能是否可用。
  - **桌面版**:有自己的跨会话功能,能查看并给**桌面版里的**其他会话发消息(显示为带来源的卡片),但看不到终端里的 CLI 会话;和 CLI 会话互通走上面那套通用跨会话消息。
  - 两种都只传纯文本,不传对话历史或文件;收到消息的 session 仍按它自己的权限规则行事。
- 契约中途变更,立刻通知受影响的棒,别等它做完再返工。
- **在途棒正在做的活,总调度不许亲自上手重复做。** 要改方向就发消息;等不及就先停掉那个棒再接手——绝不双线改同一批文件。

后来又补了五条统筹纪律(共享部署位只由统筹合入 / 单实例资源排号 / 出包归统筹 / 接棒点名超期件 / 删 worktree 两道预检),以及「转述的批准算什么」这条授权边界——全文在规则库 [A13](#a13--总调度多-session-打法增补) 和 [A14](#a14--授权边界)。统筹的全流程见 [图 ③](flowcharts.md)。

## 10 · 子 session ≠ 子 agent:一字之差,额度天壤

这两个东西经常被混为一谈,但从生命周期到计费都完全不同:

| | 执行棒(子 session) | 子 agent |
|---|---|---|
| 是什么 | 独立的 Claude Code 会话 | 会话内派出的临时子任务 |
| 上下文 | 自己完整的一套,随会话持续积累 | 不带主会话的对话历史,**也不带 memory**;项目说明(CLAUDE.md 层级)重新装载一遍 |
| 工作区 | 自己的 worktree、自己的分支 | 在派它的会话的环境里跑 |
| 生命周期 | 可以跨小时、跨天,可以交接 | 活干完即散,结果只回给派它的人 |
| 适合 | 独立工单、需要「接力」的活 | 机械活:全仓扫描、批量改动、跑测试、审查二审 |

判断口诀:**这活需要独立生命周期吗?** 需要(明天还要接着做、要交接给下一棒)→ 执行棒;不需要(一次跑完出结果)→ 子 agent。

一个容易想当然的细节:**memory 不随子 agent 走**(官方行为:子 agent 装载项目说明,但不装载主会话的 auto memory;fork 出来的子 agent 例外,它继承父会话)。另一个:**内置的 Explore 和 Plan 子 agent 连 CLAUDE.md 都会跳过**(为了快和省),自定义子 agent 也可以用 `omitClaudeMd` 跳过——派它们干活时,要它遵守的规矩只能写进派单 prompt。你沉淀在 memory 里的红线和教训,派出去的子 agent 并不知道——要它遵守的规矩,写进项目说明,或者直接写进派单 prompt。

### ⚠️ 额度陷阱:子 agent 默认继承主会话的模型

这条最容易被忽视、也最烧钱:**子 agent 不指定模型时,继承派它的会话正在用的模型。** 官方的解析顺序是:① 单次调用传的 `model` 参数 → ② 子 agent 定义 frontmatter 里的 `model`(写 `inherit` 就是跟主会话)→ ③ 环境变量 `CLAUDE_CODE_SUBAGENT_MODEL` → ④ 主会话的模型。(较早的版本里环境变量排在最前,以你的版本文档为准。) 总调度用旗舰模型时,随手一句「派个 agent 帮我全仓扫一下」——那个纯机械的 grep 活,就在按旗舰档消耗你的额度,和总调度本人一个价。

规矩:**派子 agent 必须显式指定模型档位。** 机械活指定最小档,执行类指定中档;只有真需要判断力的活才允许它继承。(模型分档见第 11 章。)

### 额度经济学(所有棒适用)

心法一句:**上下文是钱。派一个 agent = 把项目级上下文重新装载一遍,这笔钱只为「你自己做明显更慢的活」花。**

- **五分钟能自己核清的,绝不派 agent。** 纠漂、查证据、翻日志 = 主会话自己 grep 自己读。派 agent 查证据最亏:烧了装载费,拿回来的还是二手结论,关键处你还得自己复核。
- **小债合订**:同仓/同域的小活打包成一棒,不许一债一棒——一债一棒等于每笔债重付一次装载费。
- **返工打回原棒**,不重开:原棒上下文还热,新棒要从零装载。
- **并发设上限**(我们家:2 个执行 + 1 个[轻查](reference.md#轻查)——轻查 = 只做只读查证的轻量棒),每单预算 = 1 执行 + 1 返工 + 1 收口小修,要超先停下报。
- **禁止孙代**:派出去的 agent 不许再派自己的子 agent。我们家真实事故:一个测试棒偷偷派了孙代,僵尸任务卡挂 11 小时,祖父会话根本停不掉它。所以派单 prompt 末尾永远带那句「全部自己动手」。这句是软闸;硬开关是环境变量 `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`——设成主会话下面允许的子 agent 层数(设 `1` 就是只许一层、不许孙代),到了层数上限 Claude Code 就不再把派 agent 的工具给子 agent(fork 除外),逼它自己干完。可以写进 settings 的 `env` 块。

## 11 · 模型调配:三档分工

订阅额度是有限资源,模型按「这活需要多少判断力」分三档:

| 档位 | 干什么 | 例子 |
|---|---|---|
| **旗舰**(最贵最紧) | 判断密集的活 | 总调度、根因分析、架构设计、要品味的文案 |
| **主力** | 执行棒的实现活 | 按 spec 写码、修 bug、写测试 |
| **小模型** | 机械棒 | 批量扫描、清单式改动、格式化整理 |

三条注意:

- **旗舰不干搬运活。** 让旗舰模型跑 grep、贴文件,是这个体系里最贵的浪费(结合第 10 章的继承陷阱——这种浪费经常是默认发生的,你根本没批过)。
- **小模型的关键结论必须自己复核**——它们省钱,但它们会编。拿 commit / 运行时去核,别直接信。
- **每个 session 第一条回复自报当前模型。** 手机上看不到状态栏,不自报你就不知道自己正在跟哪个档位说话、烧哪份额度。一句话的事,防大钱。

### 两条省钱铁律

**① 审查/二审走订阅内子 agent,不烧裸 API。** 需要第二双眼睛时,派一个订阅内的子 agent(指定另一档模型)去审——订阅内**不产生新增账单**(占的是包月额度池,额度本身仍有限,别无脑挥霍);而拿裸 API 调模型是真金白银按 token 计费。我们家为这条交过学费:一次二审图省事走了裸 API,几轮下来烧掉 ¥4-5——同样的活走订阅子 agent,一分钱账单都不会多。立下的家规:**任何会按量计费的动作,先申请再动;订阅内的活,在额度纪律内随便跑。**

**② 工具活外包给便宜模型。** 翻译、语种检测、分类打标这类无判断含量的调用,接一个便宜的外部 API(几分之一的价格),别用主力模型的额度去干。

## 12 · 文档怎么不烂掉

工单、handoff、todo 这些流程文件,都有同一个宿命:**越写越多、越多越漂、最后没人信**。我们家的看板一度膨胀到 190KB——是的,一个 todo 文件,190KB。后来立规约清到 18KB(-91%),并且再没胖回去。核心认知:

> **文档烂掉不是勤快问题,是结构问题。只要「追加」是默认动作,文档必然烂;把默认动作换成「替换 + 删除」,它就烂不起来。**

### 单一权威源(SSOT)

**同一个事实,只允许有一个权威源;别处一律链接过去。** 发现自己要在两个文件里改同一件事 = 屎山信号,立刻停下,把其中一处改成链接。每类事实指定权威:服务/端口 → 服务总览表;工单状态 → 工单文件本身;架构 → 架构文档。看板行、handoff 提到时,一律链接不复述。

### todo:看板不是史书

todo 只回答一个问题:「**现在什么状态,下一步是什么**」。历史归 handoff,细节归工单文件。写入规则:

- **更新 = 整条重写当前态。** 新状态**替换**旧状态,被取代的文字直接删——不划删除线、不留日期链、不用「→」堆演化史。演化史 git 都记着,不需要文档自己背。
- **完成 = 删行**(移一行到已完结表)。做完的事在看板上多留一天,就稀释一天注意力。
- **临时性内容自带删除条件**:在途 session 的挂牌行「收工即删」;发车货单「验收后即删」;欠账台账「做完删行,[拖龄](reference.md#欠账台账拖龄)超 3 天收工点名」。**每一行生下来就注定要死**,这是看板保持 18KB 的全部秘密。
- **禁止写入清单**:交接摘要、调查过程、方案讨论、commit 列表、任何「留档」——这些各有各的家(handoff/工单/git log),进看板就是垃圾。
- 收工跑一个**看板守卫脚本**,而且它给的不是「参考数据」,是**硬失败条件**。

#### 看板守卫:任一项大于 0,当场修完再收工

| 硬失败项 | 判据 |
|---|---|
| trail 条目 | 顶部出现「上一份 / 同日 / 最新交接」这类堆积的交接摘要行 |
| 删除线 | 全文出现 `~~…~~`(规约要求被取代的文字直接删) |
| 超长看板行 | 看板分区里任一行超过上限(我们家 300 字符) |
| 指针链超限 | 顶部「最新 handoff 指针」超过 N 条(我们家 8 条;更早的按文件名日期找) |
| 看板分区识别失败 | 找不到或找到多个看板分区标题——**守卫自己的口径失效了,不许静默报 0** |

为什么要「硬」:我们家的守卫一开始只输出数字、「观察趋势」,结果数字一直在、看板照样胖。观察期满、确认不反弹后,才把它升成硬规:**任一项 > 0 = 收工被卡住**,修完再走。最后一项是吃过亏补的——有一次看板改了标题格式,守卫的口径恒等于 0,把一行 324 字符的超长行报成「0 个超标」,假绿了好几天。

两个坑,都是真踩过的:

- **在 worktree 里跑守卫,要显式指定仓路径。** 守卫脚本默认读主仓的看板;你在 worktree 里改了看板却跑默认路径,它检查的是主仓那份旧文件——**假绿**。我们家的守卫用一个环境变量指定仓根(`<GUARD_REPO>=<你的 worktree>`),worktree 里跑必带。
- **脚本批改看板,要按段落限定、断言只命中一处。** 同一个工单号会同时出现在看板、欠账台账、验收清扫单、已完结表好几个分区里。按「行首匹配第一个」去删,删掉的是台账行而不是看板行——我们家一个晚上犯了两次。正确写法:先用分区标题切出范围,只在该段内找行,`assert len(hits) == 1`;脚本任一步失败,后面的 `git add / commit / push` 不许照跑(别用 `;` 串,也别吞掉脚本的退出码)。

### handoff:单一入口 + 月度归档

- **活区只留当月**,更早的移进归档区(进去即冻结,只查不改)。
- 找「最新交接」只有一个动作:**按文件名日期取最新那份**。不需要目录、不需要索引——唯一入口本身就是防漂。
- handoff 是**历史线索,不是现状事实**(真值层级里它排在代码、现状文档之后)。下一棒读它知道「上一棒做到哪、为什么」,关键事实回代码和运行时核,不照抄。

### 归档前查运行时依赖

移动/改名任何文档前,先 grep 代码里有没有脚本在读它。我们家真实事故:一个工单完结归档,第二天一个定时任务断粮——它每天要读那份工单里的一个章节。**工单完结 ≠ 文件可以挪。**

## 13 · 记忆与身份:换模型也换不掉的工程师

最后一块拼图:**session 会结束,模型会换代,凭什么这套流程不散?**

### memory:一事一文件

Claude Code 有持久 memory 目录,我们家的用法:

- **一条事实 = 一个文件**,带一行 description;一个 `MEMORY.md` 索引,每条一行,session 启动自动加载索引,按需读全文。
- 最值钱的类型是 **feedback**:每次翻车、每次被纠正,复盘写成一条——**是什么 + 为什么 + 下次怎么做**。它不是日记,是补丁:下个 session 自动带着这条教训开工,同一个坑不踩第二次。
- 一条元规矩:**memory 是启动提示,不是又一套真相。** 服务状态、架构现状这些会变的事实,memory 里只留指针指向权威源,不留可以独立漂移的副本——否则 memory 自己就成了第 12 章要治的那种烂文档。

### 身份:信流程,不是信某个模型

打法手册开头那句话值得再抄一遍:

> **模型会换,工程师不换——读完这份,你就是那个工程师。**

「那个工程师」不是某个模型版本,而是 **打法手册 + memory + 文档体系** 的总和。真实发生过的场景:底层模型换代当天,新模型开一个 session,读完手册和 memory,直接接棒干活——手法、规矩、对人的了解,全部延续,像同一个人换了台电脑。

这也是整套体系最后落脚的地方:**对 AI 的信任,从「信这个模型」换成「信这套流程」。** 模型是会换的、会犯错的、会失忆的;流程是攒出来的、结痂的、只增不减的。你花在立规矩、写 skill、沉淀 memory 上的每一分钟,都在给下一个 session、下一个模型、下一年的自己存钱。

## 14 · 踩坑以后怎么防复发

前面每一章都在讲「规矩」。这一章讲规矩是**怎么长出来**的——一次事故,怎样变成一条再也不会被踩第二次的规则。只有「出事后修得快」不算好好做,**「出事前拦得住」才算**。

完整闭环见 [图 ⑤](flowcharts.md)。七步:

### 14.1 闭环七步

**① 事故:当场停,置顶报。** 发现自己造成了事故(删错数据、切断了在途请求、发错了版本),第一动作是停手、在回复最顶上用一句话报清楚「发生了什么 + 影响范围 + 现在状态」。**不许轻描淡写**——「小问题已处理」这种措辞会让人错过止损窗口。

**② 当场止血:止对地方。** 止血也要先查,三件事做完再动:
- 读这个机制的设计记录和已知失配史(原意是什么、以前怎么坏过);
- 拿日志 / 库**实证**对上具体病根,而不是症状;
- 方案里写明「不动什么」。

反例是我们家一次差点发生的事:某个定时任务和一个缓存对不上,第一版止血打算改定时时刻和阈值;重读机制史后发现真病根是另一个任务把数据「掐头」了,改时刻只会把病挪个地方。修复如果要等部署窗口才能生效,同时写好**空窗防护**([A8](#a8--修复空窗防护))。

**③ 查病根:不许写「原因不明」。** 排查报告禁止以「不知道为什么 / 无法解释」收尾——解释不了,说明**观察面缺了**:改写成「现有日志 / 指标钉不到,缺 X 探针,补法 + 成本如下」,把探针当成[一刀](reference.md#刀)去做。结论分三层标注:**确证**(对账到数)/ **高置信推断** / **待探针**,不混写。看趋势类问题(命中率、成本、失败率),窗口至少一周,单日数据只用来定位单个事件。同一个问题第二次报回来,停止打补丁,先查资料、先复现([A11](#a11--同一-bug-二报即停))。详见 [A16](#a16--可解释性与终稿只放验证过的)。

**④ 写成规则:可测,不写忠告。** 「以后注意 X」不是规则,是忠告——它能被三种方式各自「合理地」误读。规则要写成:**显式状态 + 事件表 + 判定函数 + 已知错法清单**([A10](#a10--规则写成可测模型))。同时**治全类,不缝单个**:先问「这是哪一类错法、同类还有谁会踩」,grep 全仓同类残留,修法对整个家族生效。

**⑤ 能落成守卫的,落成会拦人的代码 / 测试。** 文字规则靠自觉;守卫靠物理。判断标准:这条规则**能不能被机器判定**?能,就写成测试 / 脚本,让违反它的人(或 AI)在提交前就看见红。下一节是我们家已经落地的九个守卫。

**⑥ 收工自查。** 有些规则判定不了(「今天有没有把范围切小」),那就**焊进收工 checklist**:走单即触发,不靠记性。我们家第 0 步「范围守恒」、第 0.5 步「装载守恒」、第 7 步「收工文档递审」都是这么来的(第 7.3 节)。

**⑦ 规则本身的维护。** 规则也会烂:
- **权威源唯一**:一条规则只在一个文件里写全文,别处一律链接。要在两处改同一条规则 = 屎山信号。
- **发现漂移就统一**:两份文档对同一件事说法不一,立刻收敛到权威源,另一处改成链接——别「两边都补一句」。
- **条件式规则写清切换条件**:比如「部署代价低时放宽窗口,代价变高时自动恢复冷窗」,条件写在规则里,不需要谁记得改回来。
- **memory 只指路**:教训沉淀进 memory 时,只写「是什么 + 为什么 + 怎么做 + 权威在哪」,不复制会漂移的全文。

### 14.2 我们已经落地的守卫(脱敏通用例子)

下面九个守卫在我们家都已落地(八个是测试 / 脚本,第 5 个是命令模板;第 1 个有一部分项还是「规约硬、代码报数」,文中写明了)。源码在我们家的私有仓库里,不在本仓;这里只写脱敏后的通用形态,方便你照着改。每个都按「防什么 → 怎么拦 → 骨架」讲。

#### 守卫 1 · 看板守卫(硬失败)

`通用` **防什么**:看板一点点胖回去;以及守卫自己的口径失效后「假绿」。

**怎么拦**:收工时跑一个只读脚本,统计看板的 trail 条目、删除线、超长行、顶部指针链长度。我们家的实现里:
- **看板分区标题识别不到或重复 → 非零退出**(守卫口径失效不许静默报 0);
- **顶部指针链超过上限 → 非零退出**;
- trail / 删除线 / 超长行逐项输出计数和行号,规约规定**任一 > 0 就当场修完再收工**;
- 遥测日志路径**拒绝落在仓内**(守卫自己也不许往仓里写东西);
- 仓根路径由环境变量指定,**worktree 里跑必须指向 worktree**,否则读的是主仓旧文件。

```python
# 骨架:关键是「口径失效 = 失败」,而不是「口径失效 = 0」
heads, total, over = board_stats(lines)        # 纯函数,可单测
if heads != 1:
    fail("看板分区标题匹配 %d 个(应恰 1)——守卫口径失效,先修守卫" % heads)
if pointer_chain > POINTER_CHAIN_MAX:
    fail("顶部指针链超限")
report(trail=..., strikethrough=..., over_length=over)   # 规约:任一 > 0 当场修
```

如果你从零写,建议把这五项**全部**做成非零退出——我们家是先观察、后升级,所以有一部分还留在「规约硬、代码报数」的形态。

#### 守卫 2 · 测试写入绊线

`有测试套件` `有生产数据` **防什么**:测试经过某条路径**可写打开了生产库**并跑了迁移,而业务代码里的 `try/except` 把错误吞了,测试一直是绿的。

**怎么拦**(放在仓根 `conftest.py`,所有测试自动生效):
1. **环境变量哨兵**:每个指向库 / 数据目录的环境变量,在收集期就被**硬赋值**成一个不可能存在的路径(如 `/nonexistent/<名>-test-guard`)。需要真库的测试自己 `setenv` 到 `tmp_path`。注意是**置成哨兵值,不是删掉**——删掉的话,测试模块 import 时的「加载 .env」会把真值灌回来。
2. **审计钩子绊线**:`sys.addaudithook` 监听 `open`(写模式)、`sqlite3.connect`、`os.mkdir / remove / rename / truncate` 等事件;目标落在**仓内 `data/`**(在 worktree 里,**连同主 checkout 的 `data/`** 一起)或哨兵目录,就记一笔。只读打开(`mode=ro`、`'r'`)不算。
3. **判红**:autouse fixture 在每个测试结束时检查记录,有命中 → 该测试失败,报出路径;收集期 / 高 scope fixture / 后台线程里的命中记为「孤儿」,整轮收尾判失败。**业务代码吞没吞错都逃不掉。**
4. **锚点**:仓根放一个 `pytest.ini`,保证从任何子目录起跑,rootdir 都是仓根、根 `conftest.py` 必加载;老 worktree 缺这个锚点时 rootdir 会漂到主 checkout,直接拒跑。
5. **已知盲区写在注释里**:子进程不继承审计钩子(环境变量哨兵仍继承)。

```python
# 骨架
os.environ["APP_DB_PATH"] = "/nonexistent/app-db-test-guard"   # 哨兵:置值,不删

def _hook(event, args):
    if event == "open" and _is_write(args) and _under_data(args[0]):
        (_hits if _in_test else _orphans).append(args[0])
    # sqlite3.connect / os.remove / os.rename ... 同理
sys.addaudithook(_hook)

@pytest.fixture(autouse=True)
def _tripwire():
    ...; yield; ...
    if _hits: pytest.fail("测试可写打开了仓内 data/,请钉到 tmp_path: ...")
```

规矩:**绊线报红 = [写口](reference.md#写口绊线)漏钉**,修法是把库钉到 `tmp_path`,**不许绕过绊线**。

#### 守卫 3 · worktree 里不准往仓内落文件

`有测试套件` **防什么**:守卫 2 是「已知写口逐个钉」,新写口漏钉照样全绿。某个后端服务的测试套件里,交叉审查翻 worktree 才看见一个日志文件被测试写进了仓内——在主 checkout 上跑,它写的就是生产日志。

**怎么拦**:一道**不认名字**的兜底——
- 每个测试前后,对仓内全部文件拍快照(相对路径 → 大小 + mtime),多了 / 变了 / 少了任何一个,该测试判红并列出路径;
- 会话开始再拍一次总快照,会话结束整体比一次,兜住收集期 import 和晚于 teardown 的写入;
- **只在 worktree 里启用**(`.git` 是文件而不是目录):主 checkout 是部署位,服务一直在写,逐例比对分不清是谁写的;主 checkout 本就不许跑全量测试,那一层靠纪律;
- 会话开始先**预建** `data/`、`logs/`:有一类写口在父目录不存在时会静默失败,新 worktree 没有这些目录就写不进、也就抓不到,而主 checkout 恒有它们就真写。预建之后,这类写入在 worktree 里也能落下、被抓到。

#### 守卫 4 · 工具体积预算

`有 AI 工具面` **防什么**:给 AI 助手加工具时,描述越写越长。有一天量出来,某个助手开场的工具定义占了上下文的近一半,只能回头逐个瘦身。

**怎么拦**(两个仓各守各的,口径相同):
- `size = len(description) + len(json.dumps(input_schema, ensure_ascii=False, separators=(",", ":")))`,字符量作 token 的代理(测试里不调 API);
- 两档预算:普通件、复杂件(顶层参数 ≥ 6 个,或含嵌套对象 / 条件 schema——schema 本身就大,不是描述写长了);
- **存量超标件进白名单记当前上限,只许降不许升**:涨了红;降进预算了要删白名单行;降幅超过容差要把上限下调到当前值(**棘轮锁住成果**);
- 新工具不在白名单且超预算 → 直接红;
- **工具面自动发现**:枚举所有定义了工具 schema 的模块,新模块绕不过去;只按条件开放的模块必须登记开闸方式,否则红;
- 守卫自带负路径用例:构造一个超标工具,断言守卫报它。

规矩:守卫红了**先瘦描述**(只写字段语义和边界,不写行为指导、长示例),不许改预算放行;改预算 = 改整仓门槛,要人拍。

#### 守卫 5 · 发布命令内断言 HEAD

`有部署` `多 session` **防什么**:核完「要发布的是哪些提交」,到真正执行发布之间隔了几分钟,另一个 session 往共享部署位合入了十几个提交,被这次发布一并带了出去。

**怎么拦**:这一个我们家落在**命令模板**层,而不是脚本——断言和发布写在同一条 shell 命令里:

```bash
cd <部署位> && if [ "$(git rev-parse --short HEAD)" = "<核过的SHA>" ]; then
  <发布命令>      # 退出码就是发布命令自己的,失败不会被误报成「HEAD 变了」
else
  echo "HEAD 变了,停——先看多出来的提交是谁的、人拍过没有" >&2; false
fi
```

断言失败 = 先查多出来的提交归属,再报人,不许「顺便一起发了」。

#### 守卫 6 · 重启前查在途流量

`有长驻服务` **防什么**:重启杀死了正在生成的那一轮请求。第一次是没查;第二次是**查了**(在途 = 0),但查询和重启是两条命令,中间隔了十几秒写汇报,正好用户发起了新一轮——被切断。**检查没有原子性 = 没检查。**

**怎么拦**:一个守卫脚本,`set -euo pipefail`:
1. 读服务的请求流水,取最后一轮的时间戳;**读不到 → fail-closed,不重启**;
2. 距今小于窗口(我们家 120 秒)→ 拒绝重启,非零退出;
3. 放行后重启,然后轮询健康检查,超时非零退出并提示去看服务管理器。

它自己也踩过三次坑,值得你一起抄走:
- **守卫给的保证是假的,比没有守卫更危险**:最早手敲的守卫把秒级时间戳当日期字符串解析,失败算出 -1,于是「永远放行」;
- **守卫接管道,退出码被吞**:`guard.sh | tail` 让守卫的失败被 `tail` 的成功盖掉,后面的重启照跑——守卫命令永不接管道,或者 `set -o pipefail`;
- **只看「最后一轮起跑时刻」有盲区**:能跑好几分钟的长轮,起跑超过窗口后仍在飞,守卫会放行。更稳的判据是直接查「状态为进行中」的请求行。

#### 守卫 7 · 弹窗里的输入件必须带特定参数

`通用`(前端)**防什么**:移动端的模态窗是独立的原生窗口,键盘适配组件收不到里面的焦点事件——页面容器组件放进模态窗时如果不传一个特定参数,里面的输入框就会被键盘盖住。这种问题只在真机 / 模拟器上肉眼可见,单测永远绿。

**怎么拦**:一个**全仓扫描测试**:
- 纯函数 `screensInModalWithoutFlag(src)`:逐行跟踪 `<Modal>` 的嵌套深度,深度 > 0 时出现的容器组件,没带那个参数就记下行号;
- 第一个测试用三段小样本验证判定函数本身(模态内裸用 → 报;带参数 → 不报;模态外 → 不报);
- 第二个测试遍历全部源码文件,断言命中列表为空。

这是「把一次真机 bug 变成全仓规则」的最小范式:**判定搬进纯函数,先测判定,再扫全仓。**

#### 守卫 8 · 标记统一治理的注册表矩阵测试

`有 AI 工具面` **防什么**:我们让 AI 在输出里写行内标记(形如 `[动作名]…[/动作名]`)来触发动作。同一个错法家族(无闭合吞掉后面的标记、单行写法被静默丢弃、提及被误判为失败……)先后出了五次,每次只修出事的那一个标记。

**怎么拦**:
- 所有标记登记在一张**注册表**里,每个标记带「形状」(成对 / 单行带参数 / 单行带正文);
- 测试**遍历注册表动态生成矩阵**:每种形状 × 每条已知错法,各一个参数化用例;
- 核心断言是一条机器可判定的铁律:**认识的名字写坏了,必须落进「执行 / 判为提及 / 失败回执」三格之一,不许静默**;
- 历史事故各钉一个回归用例;
- **新增标记只需进注册表,矩阵自动覆盖**——新标记再踩旧坑,这里先红。

#### 守卫 9 · 字体守卫

`通用`(前端)**防什么**:两类事故。其一,设计稿用了某款字体,上线时手机上没有,**静默回落成系统黑体**——等于把拍过板的设计悄悄改了。其二,从可变字体切出来的几个静态字重沿用了同一个内部名,iOS 按内部名认字体,把它们当成同一款,半粗显示成了细体。

**怎么拦**,两个测试:
- **白名单测试**:扫某个页面目录下全部源码里的 `fontFamily`,只允许锁定的那几族(系统自带 + 已打包),出现别的就红;同时断言 app 配置里内嵌的字体文件恰好是那几个,且文件真实存在、大小正常。
- **打包字体测试**:直接解析每个字体文件的 `name` 表,读出 PostScript 名(name ID 6,Mac / Windows 两套记录必须一致),断言**两两不同**且**等于代码里引用的字体名**;字体登记表里恰好是这几款、标为已打包;开源许可证随包。

规矩:某款字体确实上不了(授权禁止打包等),按「偏离已定方案」报人重拍,**绝不自行换字体**。

### 14.3 守卫的共同设计原则

从这九个里提炼出来,写新守卫前过一遍:

1. **fail-closed**:守卫自己读不到数据 / 口径失效时,结果是「拦」,不是「放」。
2. **守卫给的保证必须是真的**:假守卫(永远放行、只深查一张表、快照有假阳性)比没有守卫更危险——它让人放心地做错事。所以**每个守卫都要有负路径自测**:真造一个违规,看它报不报。
3. **不认名字的兜底**:逐个钉已知写口之外,再加一道按「结果」判定的兜底(快照对比、全仓扫描),新漏洞也跑不掉。
4. **棘轮**:存量问题进白名单,只许降不许升,降了就锁住。
5. **检查和动作同一条命令**,并且守卫命令不接管道。
6. **报错信息就是修法**:红的时候直接告诉人「把库钉到 tmp_path」「从白名单删这一行」,不让人猜。
7. **盲区写进注释**:守卫拦不住什么,写清楚,别让下一个人以为它全能。

### A1 · 完整交付律

`通用`

**规则**:
1. 人拍过的范围是**不可缩减的整体**。执行中缩范围、拆期、把子项转成「欠账 / 二期 / 等拍」= 偏离已定方案,必须拿到人**新的**明确拍板。方向永远是:**完整交付是默认,「不做完整」才需要审批**——不是反过来。
2. **成本估算只在立案前影响范围;立案后,成本只是信息。** 实际成本远超预估 → 报人重拍,不许自行缩;发现「这块好像可以不做」→ 报告,不许自作主张剪。用账劝退已拍的需求 = 违规。
3. **工期默认当天。** 不需要观察期 / 外部等待的工程当天推完;跨天必须写明物理原因(等部署窗口、外部依赖、等人在场)。「工作量大」不是理由——工作量大就拆成并行的棒,不是拆成几天。
4. **观察期只验证已做的**,永远不作为「暂缓做下一件」的理由。
5. **收工自查**:今天有没有把拍过的范围切小 / 推迟?有 → 收工总结显性点名 + 原因。

**为什么**:有一个需求,人提出来之后被 AI 一方用一笔「成本账」劝退,搁置了二十天——期间它本来要治的那项开销每天还在涨,是人自己发现的。人的原话大意是:「我的需求总被切成 30% 加 70% 的 30%,永远做不完。」病根是规则方向反了:**切小被当成安全的默认,做完整反而要审批。** 之前加过好几条「别拖延」的规矩都治标不治本,因为它们治的是形态,没治方向。

还有一种隐蔽版:分刀的时候,方案里写过「这一项放到第 N 刀」,到了第 N 刀写方案时只照着当刀的清单列,**漏掉了前几刀承诺放过来的项**。

**怎么落地**:
- 写进项目说明,并在收工 checklist 加第 0 步(第 7.3 节);
- 每一刀写方案前,先把设计单的对照表、拍板表、前几刀方案里「放到本刀」的条目**逐条列出**,复述时标「本刀覆盖 / 不覆盖(原因)」;
- 已经拍过的刀,下一步只能是「出方案给人审」,不是去问「这刀还做不做」。

### A2 · 需求复述闸

`通用`

**规则**:
1. **别按「标准需求文档」的形状去过滤需求。** 需求方的表达可能零散、非线性;**形状不常规 ≠ 需求不完整**。别拿工程直觉把「不合常规形状」的部分剪掉,把每一条都列进复述表。
2. **动手前逐条复述**:「你要的是 1 / 2 / 3」,并标明方案覆盖哪条、未覆盖哪条及原因。**省略必须显性摆在人眼前由人裁**,不许静默剪裁。人确认后才动。
3. 人的话里带问号或情绪信号时,**先接住再谈方案**。

**为什么**:AI 在转译需求时会静默剪掉它认为「不重要」或「不像需求」的部分,做完才发现漏项,只能返工;口头提醒「别漏」没有用。改成**结构保证**之后——不复述就不准动手,省略不摆出来就不准省——漏项在动手前就暴露了。

**怎么落地**:
- 写进项目说明的「接需求」条款,和 A1 配套;
- 工单模板加「需求复述」表:原话条目 / 本单覆盖? / 未覆盖原因 / 人的裁定(见[工单模板](../templates/ticket.md));
- 合并类需求(「把 A 页和 B 页放到一起」)先列「旧页每个控件 × 新处有没有」的对照表再复述。

### A3 · 装载三层验证 + 收工装载守恒

`有部署`

**规则**:「已装载 / 已生效」不是一句话,是三层实据:

| 层 | 判据 |
|---|---|
| ① 进程层 | 该重启的每个进程,**启动时刻 = 这次发车时刻**(`ps -eo pid,lstart,command`),只看部署日志里写「已重启」不算 |
| ② 代码层 | **逐仓** `git rev-parse HEAD` 精确等于货单钉的 SHA。多仓改动每仓都比——只装了一仓 = 没装载 |
| ③ 产出层 | 货单**逐件**验一条**生产真输出**(一条 SQL / 一次 grep / 一次只读调用),判据在货单登记时就写好 |

- 「已装载」= ①② 齐;「已生效 / 已上线」= ①②③ 齐。实据不够就写「候装载 / 候验证」。
- **共享模块的装载面 = 全部宿主进程**:改了被多个进程 import 的模块,先 grep 出全部宿主,逐个比启动时刻,漏一个 = 没装载。
- 产出层判据要钉在**用户真正在用的那条链路**上,备用链路验过不算数。
- **收工装载守恒**:今天产生了候车货 → 下一班车必须**确实已挂**(按确切的任务名核两处:任务定义文件存在 + 服务管理器里已加载);拆掉跑完的旧车时,同一个动作里核对还有没有候车货。

**为什么**:两件事同一天被人抓到。一件是两个 session 各自拆了旧的定时装载任务、谁也没挂新的,全部候车改动晾了一夜——文档里还写着「走常规冷窗机制」,而那个机制根本不存在,每一班车从来都是逐日单独挂的。另一件是一个跨两仓的改动只装了一仓,某个字段恒为空三天,所有机器检查都绿,因为功能设计成了「无害降级」,安静空转。还有一次,改了一个共享模块只重启了其中一个宿主进程,用户主用的那条链路两天没生效。

**怎么落地**:货单模板每行带「验证命令 + 通过判据」;[晨验](reference.md#晨验) / 部署后按三层逐件过;收工 checklist 加第 0.5 步。

### A4 · 检查和动作绑同一条命令

`有长驻服务` `有部署` `多 session`

**规则**:凡是「先检查、再动作」的操作(查在途流量 → 重启;核 HEAD → 发布;核没人占用 → 删除),**检查和动作写进同一条 shell 命令**,用 `if / else` 绑定,检查失败动作就不发生:

```bash
if [ "$(查在途数量)" = "0" ]; then 重启服务; else echo "有在途,不重启" >&2; false; fi
if [ "$(git rev-parse --short HEAD)" = "<核过的SHA>" ]; then 发布; else echo "HEAD 变了,停" >&2; false; fi
```

用 `if / else` 而不是 `检查 && 动作 || echo`:后一种写法在**动作本身失败**时也会走到 `echo`,把「重启失败」误报成「有在途」,而且因为 `echo` 成功,整条命令返回 0——失败被吞了。

另外两条配套:**守卫命令永不接管道**(`| tail` 会吞掉退出码,要么 `set -o pipefail`);**链式命令里退出码要紧的环节,要取输出就分步写**。

**为什么**:检查和动作隔两条命令,中间哪怕只有十几秒(AI 在写汇报),世界就可能变了——我们家因此切断过一次用户正在进行的请求,也因此把别的 session 刚合入的十几个提交一起发了出去。这是经典的 TOCTOU(检查时刻 ≠ 使用时刻)。

**怎么落地**:把常用的「检查 + 动作」写成守卫脚本或命令模板(见第 14.2 节守卫 5、6),项目说明里只放模板,不放裸动作命令。

### A5 · 副作用重试前读回 + 按实际副作用分类

`通用` · 取自开源仓 [**astrean-worker-lanes**](https://github.com/LuluaneS/astrean-worker-lanes)(我们严审了这个仓,吸纳了其中两条,其余同构件我们已有)

**规则**:
1. **有副作用的调用报错 / 超时 ≠ 没发生。重试前先读回一次现状。** 发消息超时、发布无回执、远程调用超时、派任务无响应、服务管理器报了含糊的错——第一次调用可能已经成了,盲目重发 = 双投递。重试前用**该动作自己的只读口**核目标状态或唯一标识(消息 → 对端收件箱;发布 → 发布记录列表;派任务 → 任务列表;进程 → `ps`)。**只有拿到「明确未发生」的证据才重试**;确认成了就改做收尾;读回结果拿不准就停下汇报,不赌。
2. **「只读」按实际副作用分类,不按动词分类。** 「查状态 / 读文件」不天然只读。真实存在的「假只读」:一个查状态的接口,被调一次就会补投一条本该只发生一次的初始化事件;一个读数据的工具,被调用时会回写元数据字段;一个函数的默认参数指向生产库,实例化就跑迁移。

**为什么**:重复的消息、重复的发布,对用户是可见的;而「我只是查一下」恰恰是接棒核查、晨验、审计时最常说的话——如果那个「查」会写东西,只读核查本身就成了事故源。

**怎么落地**:
- 项目说明里维护一份「假只读件名单」(只放一处,别处链接);
- 给审查方 / 子 agent 下「只读核查」指令时,把名单一并递过去;
- 调用按量计费 API 的「读」也有成本,同样受花钱红线管。

### A6 · 测试写入绊线 + dotenv 爬出 worktree

`有测试套件` `有生产数据`

**规则**:
1. 测试套件里装一道**写口绊线**:任何测试可写打开仓内数据目录(在 worktree 里,连同主 checkout 的数据目录)= 该测试判红,业务代码吞没吞错都逃不掉。绊线报红 = 写口漏钉,修法是钉到临时目录,**不许绕过**。
2. 每个指向库 / 数据 / 外部服务 URL / 凭证的环境变量,收集期就**硬赋值成哨兵**(不可能存在的路径、空 URL)。**新增一个会外呼 / 会花钱的环境变量时,把它加进哨兵名单是落键动作的一部分**,不是事后补。
3. **worktree 不隔离 dotenv。** 动手前想一遍:这个仓有没有「无参加载 .env」(会从当前目录逐层往上找)、或者「按绝对路径加载主仓的 .env」?

**为什么**:两起。一起是业务代码顶层有一句无参的 `load_dotenv()`,worktree 嵌在主仓目录下,测试进程一路向上吸到了主仓 `.env` 里的生产服务地址和凭证,一个新加的「双写」功能在跑测试时**真的 POST 到了生产服务**,两条测试数据落进生产表。另一起更隐蔽:某个模块按**绝对路径**加载主仓的 `.env`,worktree 隔离对它天然无效,测试造出来的假事件被真投递到了生产,用户连着看到了好几天。

**怎么落地**:骨架见第 14.2 节守卫 2、3。哨兵是**置值不是删除**——删了会被 import 期的 `load_dotenv(override=False)` 灌回来。

### A7 · 审查方选择与兜底

`有审查方`

**规则**:
1. **按审查对象选审查方**:
   - 纯代码 diff → 沙箱里的异构审查方(如 Codex)最好;
   - 涉及**运行时实况**(进程、端口、服务管理器、定时任务、真实库、用户级服务)→ 必须交给**能进真实环境**的审查者(如跑在你机器上的订阅内子 agent,指定强档模型)。
2. **额度兜底**:异构审查方额度用完时,用订阅内子 agent 兜底,不跳审、不走按量计费的裸 API。
3. **修法回递终审**:审查方提的修法(「建议加 X」)实现之后,终版必须回递一轮;「它指了方向」≠「它审过实现」。
4. **审查方的回执要核查,不盲从**;它的判断有误就摆证据二审 / 反驳。
5. 审查方自己也要知道边界:看不到的东西报「本环境无法验证」,而不是报「阻断」(见 [AGENTS.md](../AGENTS.md) 的 Sandbox Limits 一节)。

**为什么**:一次部署方案的审查里,沙箱审查方报了「服务未加载 + 端口不通」两条阻断——全是它自己环境的假象(沙箱里看不到用户级服务、连不了本地端口)。当晚换了能进真实环境的子 agent 复审,反而抓出了一条真阻断:审查方上一轮建议的修法,被实现时写反了。另有两次,审查方只建议了方向、没见过最终实现就合并了,事后补审才过。

**怎么落地**:见 [review-protocol 的「审查方选择」](../conventions/review-protocol.md#审查方选择) 和 [审查 checklist](../templates/review-checklist.md)。

### A8 · 修复空窗防护

`有部署` `有生产数据`

**规则**:已经确诊的生产问题,修复要等部署窗口才生效时,工单必须写一行「空窗防护」,三选一:
1. **防护措施**(数据止血 / 临时降级 / 看护脚本)+ 重跑节奏;
2. **明写「防不了」+ 预计影响**,交人拍:忍到窗口,还是破例提前发;
3. **当场装上**(人拍了破例时)。

没有这一行 = 不合格工单,审查方按阻断提。部署后的晨验要查「病人」:每个已知在产的问题,查它**过去 24 小时的生产实据**(疼了没疼),不只验机器。

**为什么**:有一组问题确诊后修复在等班车,两周里没人排防护,生产上一直在疼;最后是人从产出里自己发现的,而不是从 AI 的晨验报告里。晨验当时只验了「车发了没、分支对不对」,没验「病人好没好」。

**怎么落地**:工单模板加这一行(见[模板](../templates/ticket.md));审查 checklist 加一项。

### A9 · 防在前面

`通用`

**规则**:**只做「出事后修得快」不算好好做,「出事前拦得住」才算。** 四个具体动作:
1. **静默失败 = 阻断级设计缺陷。** 凡是 AI(或用户)能主动触发的动作,失败必须给**触发方看得见的回执**(哪条没成 + 为什么 + 候选),v1 就要有,不许「先上成功路径」。
2. **修复空窗必配防护**(A8)。
3. **晨验必含[病人项](reference.md#病人项)**:每个已知在产的问题查过去 24 小时的生产实据。
4. **压力集必含失败路径用例**:测试不只测「认不认得上」,还要断言「认不上时触发方看到了什么」——断言回执内容,不许断言静默。

**为什么**:一组动作失败时什么都不说,AI 就从沉默里「学」到了错误的规则,接下来的输出被污染成了猜谜;五个问题是一个个疼出来、被人发现之后才修的。

**怎么落地**:设计审 / 代码审把「静默失败」列为必查项;遥测类功能的验收标准写「生产日志里真出现了这一行」,而不是「测试绿了」——我们家吃过亏:一个自定义 logger 没人配 handler,INFO 全被吞,而测试一直是绿的(测试框架的日志捕获根本不经过 handler 那一层)。

### A10 · 规则写成可测模型

`通用`

**规则**:规范里凡是「必须 / 不许」的规则,写成**显式状态 + 事件表 + 判定函数**,并把**已知的错误落法逐条列出**(「有人这样错过」比「不要这样」有效);要求实现方把判定搬进**可单测的纯函数**,而不是留在视图 / 业务流程里。同一概念错误反复出现时,升级成「几种错法 + 一种对法」的对照表。

**为什么**:三个客户端(三个平台)由三个独立的子 agent 按同一份算法文档实现,**三个都在同一条规则上出了错,而且错法各不相同**——三个都读过写着这条规则的坑单。那条规则当时写的是一句忠告(「翻页只认用户发起的滚动,别听惯性事件」),忠告能被三种方式各自「合理地」误读,模型不能。另一个例子:同一个跨夏令时的日期错误,在同一个仓里出现了四次(服务端算术、客户端公式、两种语言的日期库),最后靠对照表才止住。

**怎么落地**:规范 / 工单模板里,「必须 / 不许」类条目强制带「状态 / 事件 / 判定 / 已知错法」四栏;多个实现同时违反同一条规则时,先修规范,再修实现。

### A11 · 同一 bug 二报即停

`通用`

**规则**:
- 同一个 bug,人**第二次**报回来 → 停止在原方案里打补丁,先做两件事:① 查资料,找这类问题的成熟解法 / 现成库;② 在本地(模拟器 / 测试)**复现出人看到的现象**再动手。复现不出不许盲修。
- **第三次**还让人去试 = 违规,无论理由。
- 交互件(底部弹层、手势、滚动、拖拽吸附、键盘避让)**默认用成熟库**;手写必须先说明「为什么不用库」并得到同意。

**为什么**:一个手写的底部弹层拖拽状态机,「往上拉会缩回去」被报了三次,AI 改阈值、改吸附方向、改父级自动关闭,六次热更新里三次在修同一处,最后拉满了正文还滚不动。人陪着试错了一整晚。第四次换成成熟的弹层库,一次解决。根因 = 没搜库 + 沉没成本 + 拿人当测试机。

**怎么落地**:收到第二次返工反馈时,回复模板固定为「这个我先不改代码,先查 / 先复现」,然后带着一手来源或复现结果回来。

### A12 · 生产数据写入纪律 + SQLite WAL 坑

`有生产数据`

**规则(纪律)**:
1. **有统筹在场时,执行棒写生产数据(回填、UPDATE / DELETE、迁移、批量改数据文件)前先报统筹,等回执。** 即便人已经在这一棒亲口拍过,也要报——统筹要掌握全部生产写入,才能排装载顺序、防多棒撞同一个库、在交接里如实记账。
2. 报的内容三件套:**人的原话 + 备份路径(放在仓外)+ 影响行数**;改完做**逆向验证**(行数守恒、非目标列逐行不变)再回报。
3. 自动化的安全分类器拦下了生产写入,**不许绕**——出路只有人亲手跑(给最少条数、带顺序的可复制命令),或人自己加放行规则。

**规则(SQLite 迁移守卫,每条都实测过)**:
1. `sqlite3 -bail`:CLI 默认报错不停、继续跑到 `COMMIT`,`BEGIN / COMMIT` 的原子性是假的。
2. **WAL 模式下,把备份 `cp` 回去会静默无效**:陈旧的 `-wal` 文件被重放,把数据盖回去,而 `integrity_check` 照报 ok。恢复三步:停服务 → 删 `-wal` `-shm` → 再 cp,顺序不可换,判据必须真查行数。备份用 SQLite 的 backup API,不用 `cp`。
3. **服务活着时做前后快照必有假阳性**,而假阳性的处方是「cp 回滚」——**守卫自己会引人删数据**。所以服务必须先停,快照钉死在迁移前的 id 集合上。
4. 判断服务停没停,用**服务管理器**查任务还在不在(时点快照的 `pgrep` 挡不住保活重生),再叠 `pgrep` + `lsof` 看谁握着库文件。
5. `wal_checkpoint(TRUNCATE)` 的 busy 列不是独占探针——空闲但连着的连接它探不到,`lsof` 看得见。
6. 只深查一张表的守卫,对「别的表被清空」是瞎的:**全库逐表 count + 全 DDL**,并做**反向验证**(真清一张表看守卫报不报)。
7. 起服务必须排在迁移之后(新代码 + 旧库 = 每次请求报错)。
8. 迁移交付前,在**生产库的仓外备份拷贝**上实跑一遍:核全列哈希、完整性、幂等、注入失败后字节不变。测试夹具用生产 `sqlite_master` 的原文——生产里可能有历史遗留的写法(比如带引号的表名),自造夹具测不出来。
9. **全部预检做完再动 DDL,DDL 放同一个事务**——「先改一点再判定」的迁移,失败时会留下半截 schema。
10. 只读核查时,WAL 库在恰好没有连接、没有 `-shm` 文件时,用只读 URI(`?mode=ro`)打开会失败;守卫脚本里对这类库用普通打开只跑 SELECT。

**为什么**:我们家最痛的一次,是一条「先测一下」的命令在错误的目录里清掉了上千条生产记录。之后写的第一版迁移守卫被审出七条问题,其中三条是「守卫给的保证是假的」——比没有守卫更危险。后来又有一次,迁移代码只在自造夹具上测过,生产里那张表的建表语句写法不一样,正则没认出来,服务启动报错退出——而报错前已经加了一列,「失败并非不动库」。

**怎么落地**:写一个迁移守卫脚本样板 + 它的自测(含负路径:中途失败必须整体回滚),之后所有生产迁移照抄样板,别每次重新发明。测试一律在 `/tmp` 下的新目录,用完即删。

### A13 · 总调度多 session 打法增补

`多 session`

第 9 章的总调度纪律之外,后来又补了五条:

**① 共享部署位只由统筹合入。** 主 checkout 如果是部署位(合并 ≈ 装载),执行棒在 worktree 做完、测完、提交后,**不自己往部署位合入**——把「分支 / 提交 / 基于哪个主干 / 改了什么 / 测试结果 / 是否涉及装载」报给统筹,由统筹 `merge --ff-only`。如果往部署位合并就等于上线,统筹的顺序是:**登记货单 → 人的当次许可 → 守卫(在途为 0、部署位 HEAD 仍等于合并前核过的基线)→ 同一条命令里 ff-only 合并货的 SHA → 合并后核 HEAD 等于货的 SHA**(第 7.1 节)。合入后执行棒负责清理自己的 worktree(先过 ⑤ 的两道预检)。
*为什么*:部署位是多棒共享的,谁都能合 = 谁都可能把别人没准备好的东西带上线。

**② 单实例资源排号。** 只有一份的资源(唯一的一台模拟器、一个开发服务器端口、一个调试设备),由统筹按号排队分配,谁在用、用完了没,登记在案。
*为什么*:两个棒同时抢一台模拟器,一个在装包、一个在截图,两边的验收证据都不可信。

**③ 出包归统筹。** 任何构建安装包的动作只归统筹本人,执行棒一律不出包。统筹出包的前置顺序卡死:模拟器跑通 → 汇报人 → 人说「可以出包」才出。热更新发布同理:先给人看得到的东西(截图 / 预览地址),人说「发」才发,中间态不许发。
*为什么*:出包和发布直接落到人的设备上,是发布不是保存;多个棒各自出包,装到设备上的是哪一版就说不清了。

**④ 接棒汇报必须点名超期件。** 接棒汇报里有一条硬项:逐条点名台账里**拖龄超期的已拍板件**,今天排不排——排就给排期,不排写理由,不许略过。
*为什么*:「拖龄超 3 天收工点名」只管点名、不管排期;每天的棒都优先接当天的新事,结果拍过板的旧承诺一拖再拖(有的睡了九天、二十六天)。

**⑤ 删 worktree 两道预检。** 「已合并 + `git status` 干净」≠ 可以删:
1. `lsof -a -d cwd -u $USER` 有进程的工作目录在这里 → 拒删(有活着的 session 在用);
2. `git status --porcelain --ignored=matching` 过滤掉可再生的(缓存、依赖目录、本地设置)之后,仍有 `!!` 行 → 拒删并列出(那是 gitignored 的非再生文件)。
批量删除走脚本(绝对路径数组、拒删主仓和当前 session、HEAD 必须是主干祖先、先干跑),跑之前先让另一个模型复核;**worktree 只删自己开的**。
*为什么*:一次批量清理 worktree,复核抓出三条真阻断:一个 worktree 里有几十 MB gitignored 的设计原稿(全盘唯一一份,`worktree remove` 对它一声不吭);两个「干净」的 worktree 里正跑着活 session。

### A14 · 授权边界

`通用`

**规则**:
1. **转述的批准只算「可以排上」,不算「现在做」。** 别的 session 转达「人已经拍了」,授权的是「货可以上车」,**永远不授权时机**——哪怕转达的原话是「时间归你定」。时机类动作(重启、发布、出包、花钱)只认人在当前对话里的字面许可;唯一的例外是人预先约定好的定时冷窗车,那个时机人已经拍过。
2. **「为什么还没 X」是疑问,不是命令。** 回答原因、把 X 的前置条件摆出来,等人给动词。
3. **提问 ≠ 拍板。** 人把选项词原样打出来(「选 B,整表关档」),可能是在问这些词什么意思。没有明确的动词(「就这样 / 跑 / 执行 / 发」)或带问号时,先解释 + 确认再动。
4. **人问进度 ≠ 推进授权。** 调查答完就停,立新单 / 占号也要人拍。
5. **许可一次一发,不留存。** 「上次说过可以」不覆盖这一次。
6. 已经抢跑了 → 立刻主动坦白 + 给回滚口。

**为什么**:三起。一起是别的 session 转达「人已拍排进班车,时间归你定」,接到的 session 当即白天重启了服务——人原话是「我不是说除了凌晨不准发吗」。一起是人问「为什么你这个还没发」,AI 读成指令发了热更新,随包带出了别的棒九个没发过的提交。还有一起是人把待拍的选项词照抄过来追问含义,AI 当场执行了三项。

**怎么落地**:写进项目说明;给统筹 / 执行棒的派单模板里写明「哪些动作只认人当次的字面许可」。

### A15 · 工具体积预算守卫

`有 AI 工具面`

**规则**:给 AI 助手新增或修改工具时,**设计阶段就控制体积**:描述只写字段语义和边界,不写行为指导、长示例、重复说明;参数 schema 能省则省。仓里有体积预算守卫测试,新工具超预算直接红;存量白名单只许降不许升。哪些工具常驻上下文、哪些按需加载,由人在一份唯一的名单里拍,新工具默认按需加载。

**为什么**:有一天量出来,某个助手开场的工具定义占了上下文的近一半,其中几件常驻工具的长描述是大头,只能回头逐个瘦身。人的原话大意是:「这种事应该在做工具的时候就考虑,而不是每次都要我来喊瘦身。」

**怎么落地**:守卫骨架见第 14.2 节守卫 4;新工具工单的验收里写一条「体积守卫测试绿 + 实测 token 数」(token 数用免费的计数端点量,并**注明用的是哪个模型的计量**——不同模型对同一份工具定义的计数可能差到 1.6 倍,两把尺子的数不能互减)。

### A16 · 可解释性与终稿只放验证过的

`通用`

**规则(可解释性)**:
- 排查 / 审计报告里**禁止「不知道为什么 / 无法解释」收尾**——改写成「现有观察面钉不到,缺 X 探针,补法 + 成本如下」,把观察债列成刀让人拍。
- 结论分层标注:**确证**(对账到数)/ **高置信推断** / **待探针**,不混写。口径同理:主嫌 ≠ 定案,候选 ≠ 根治,模拟器验收 ≠ 人验收。
- 看率类 / 成本类问题,窗口默认 ≥ 7 天;单日数据只做当日事件定位。

**规则(终稿只放验证过的)**:
- 交付级文档(要对外发布的教程、人要用的稿、公开 README)每句话过一遍「真的验证过吗」,**没验的不写**——连「不打包票」式的标注都不行,没验的内容属于工单,不属于终稿。
- **一个交付物只有一份权威稿**,迭代在同一份上改;中间探索稿留在草稿区自己用,不占终稿的名。
- **验证解锁制**:功能验收过了,当天把对应一节写回终稿;验收黄了,对应一节删掉。

**为什么**:一次账单审计,AI 用「不知道为什么」解释一次异常,人说:「不知道为什么,就是我们的系统做得有问题。」——异常查不到根因,病根不在异常本身,而在观察面没建。当天补了指纹探针,之后同类问题从「考古」变成「查表」。同一次还发现:只看一天的数据,把一个连续多天的集群问题看成了孤例。另一起是一份要发布的教程终稿里,混进了当天在做但没验证的内容,还同时产出了三份并行草稿——中间态堆积成了屎山,未验证的声明混进了发布物。

**怎么落地**:报告模板里固定「确证 / 推断 / 待探针」三栏;交付级文档递审时,审查方专查「这句有没有证据」。
