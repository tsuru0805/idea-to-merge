# 新手入门:从第一句话到多窗口

> 这个仓库的[进阶手册](idea-to-merge.md)很长,因为它写的是一个跑了很久、规模很大的项目。
> **你不需要一开始就用上它。** 这一页是给完全没有工程背景的人看的:从第一次跟 Claude Code 说话开始,一级一级往上爬。
>
> 每一级都写清四件事:**适合谁 / 这一级做什么 / 做到什么程度算会了 / 什么时候该上下一级。**
> 没到下一级的信号,就别急着往上爬。用不上的规矩,只会让你更累。

先认识主角:**Claude Code**(下面简称 **CC**)是 Anthropic 出的写代码助手。它能读你电脑上的项目文件,能改文件,也能跑命令。你用中文跟它说话就行。

它有两种用法:

- 在**终端**里用。终端就是电脑上那个黑底白字、靠打字下命令的窗口。这种用法叫 **CLI**。
- 用**桌面版** App,有按钮和面板。

两种用法的区别见文末[「CLI 还是桌面版」](#cli-还是桌面版)。

本页用到的命令和界面说法,都按 Claude Code 官方文档(code.claude.com/docs)写。版本更新后如有出入,**以官方文档为准**。

## 第 0 级 · 会跟 CC 说话(零配置)

**适合谁**:刚装好 CC,还没写过任何配置文件。想让它帮你做点小东西,比如「给个人博客加个暗色模式」「做一个记账小工具」。

**这一级做什么**:学会五个说话习惯 + 看懂权限弹窗。什么都不用配置。

### 习惯 1 · 一次只提一件事,并说清三样东西

每次只提一个需求,而且说清:

- **要什么**:想要的结果长什么样;
- **不要什么**:哪些地方别动;
- **怎么算做完**:你会怎么检查它做好了。

需求一大,AI 就容易「顺手」多改别的地方。一次一件事,出了问题也好找。

### 习惯 2 · 先复述、再给方案、你同意后才动手

让它先用自己的话把你的需求复述一遍,再说打算怎么做(改哪些文件、不改哪些),**你说「可以」它再动手**。复述的时候,你能一眼看出它是不是理解错了;如果它悄悄漏掉了你说的某一条,这时候也能看出来。

CC 自带一个「计划模式」(plan mode):这个模式下它只读文件、出方案,不改文件。CLI 里按 `Shift+Tab` 切换模式(或者在一句话前面加 `/plan`);桌面版在发送按钮旁边的模式选择器里选「Plan」。

### 习惯 3 · 每一步都让它告诉你怎么验证

让它在方案里写上:做完之后,**你**怎么确认它真的好了。比如「打开哪个页面、点哪个按钮、应该看到什么」。验证方法写不出来的需求,往往是需求本身还没想清楚。

### 习惯 4 · 它说「完成了」,你要追问

AI 很容易把「代码写完了」说成「功能好了」。听到「完成了」,追问三句:

- 「你测了什么?怎么测的?」
- 「证据在哪?把命令的输出 / 截图给我看。」
- 「还有什么是你没验证的?」

能拿出证据的才算完成。拿不出来的,让它补上验证,或者老实写「没验证」。

### 习惯 5 · 改坏了,叫它退回

- 直接说:「刚才的改动有问题,全部撤销,恢复到改之前的样子。」
- 你每发一条消息、让它开始新的一轮工作,CC 都会在动手之前,自动给代码存一个「还原点」。(它正在干活时你插进去的话,算在当前这一轮里,不单独存。)CLI 里输入 `/rewind`(或者在输入框为空时连按两次 `Esc`),可以选回某一条消息之前的样子。注意:还原点是**按你发的消息**存的,一条消息里它改了好几处,只能一起退回。
- **但要注意**:它通过运行命令改动的文件,这个还原点**管不到**。比如它跑了一个脚本(脚本:一个能自动执行一串操作的程序文件),脚本改的东西退不回来。想要可靠的「后悔药」,要用第 2 级的 git。

### 说法对照:从「得多说几句」到「像平时说话一样」

起步阶段,CC 还不知道你的规矩,你不得不把话说全:要什么、不要什么、怎么算做完、先别动手。等规矩攒起来(第 1 级的 CLAUDE.md、第 2 级的工单和审查),**规矩替你说了一半**,你就能像平时说话一样下需求。这正是从第 0 级爬到第 2 级的意义。

下面每张卡片是同一个场景的四种样子:容易翻车的说法 → 刚开始时得这么说 → 配好规矩以后可以这么说 → 为什么能这么说。

**场景 1**

- ❌ **容易翻车的说法**:「把博客弄好看一点。」(没说要什么、什么算做完)
- 🌱 **刚开始、还没配规矩时(得多说几句)**:「给博客加暗色模式。只改样式文件,别动文章内容。做完后我打开首页切换一下,背景应该变深色、文字变浅色。」
- 💬 **配好规矩以后(像平时说话一样)**:「我想把博客弄好看点,可以部分甚至整个推翻现在的 UI。方向我还没想好,就是觉得动效太少、页面太呆、分区太乱。」
- 💡 **为什么能这么说**:不用自己先想好方案。把痛点说出来就行,规矩里写了「先出方案给我确认再动手」。

**场景 2**

- ❌ **容易翻车的说法**:「你看着办,直接改吧。」
- 🌱 **刚开始、还没配规矩时(得多说几句)**:「先别改代码。用你的话复述一遍我要什么,再列出你打算改哪些文件、哪些不改。我同意了你再动手。」
- 💬 **配好规矩以后(像平时说话一样)**:「要改代码就先立单,改完给审查审到过。」
- 💡 **为什么能这么说**:立单和审查的流程写在 CLAUDE.md 里,一句话就能触发整套。

**场景 3**

- ❌ **容易翻车的说法**:「做一个完整的记账 App,要有图表、分类、导出、多人同步。」(一次塞太多)
- 🌱 **刚开始、还没配规矩时(得多说几句)**:「做一个记账小工具,第一步只做『记一笔:金额、日期、备注』,先不做统计图。」
- 💬 **配好规矩以后(像平时说话一样)**:「我想做个记账本,要图表、分类、导出、多人同步。你先帮我整理成需求,出个方案,顺便看看市面上有没有现成的。」
- 💡 **为什么能这么说**:一次说很多也没关系,只要让它先整理、先出方案,而不是直接开写。「先搜现成方案」也可以写进规矩。

**场景 4**

- ❌ **容易翻车的说法**:「好了吗?」(它只会回答「好了」)
- 🌱 **刚开始、还没配规矩时(得多说几句)**:「做完告诉我:你跑了哪些检查?把输出贴出来。还有哪些你没验证?」
- 💬 **配好规矩以后(像平时说话一样)**:「好了吗?工单做到哪一步了,还剩多少没做?」
- 💡 **为什么能这么说**:有工单,它就得按工单逐项报进度,不能只回一句「好了」。

**场景 5**

- ❌ **容易翻车的说法**:「顺便把别的问题也一起修了。」
- 🌱 **刚开始、还没配规矩时(得多说几句)**:「这次只改 `style.css`,其他文件一个都别碰。要改别的,先停下来问我。」
- 💬 **配好规矩以后(像平时说话一样)**:「发现别的问题先告诉我,尽量用大白话讲。太技术的我听不懂,就让审查看看这样改行不行。」
- 💡 **为什么能这么说**:规矩里写了「范围外的问题只报告、不顺手改」;听不懂的交给审查判断。

**场景 6**

- ❌ **容易翻车的说法**:「怎么又坏了,快修。」(它会在坏的基础上继续打补丁)
- 🌱 **刚开始、还没配规矩时(得多说几句)**:「刚才那一步改坏了。把这次的改动全部撤销,恢复到改之前的样子,然后告诉我你恢复了哪些文件。」
- 💬 **配好规矩以后(像平时说话一样)**:「哪里坏了?查不明白就多派几个子 agent 从不同角度查,也上网搜搜有没有人碰到过一样的问题。」
- 💡 **为什么能这么说**:「同一个问题第二次出现就停手先查」写在规矩里;子 agent 和联网搜索是它本来就有的能力。

**场景 7**

- ❌ **容易翻车的说法**:「再试一次。」(同一个问题反复试,越改越乱)
- 🌱 **刚开始、还没配规矩时(得多说几句)**:「这个报错我第二次看到了。先别改代码,先查清原因,把你的判断和证据告诉我。」
- 💬 **配好规矩以后(像平时说话一样)**:「又是这个错。先别改,跟上次一样先查清原因。」
- 💡 **为什么能这么说**:同上一条。

**场景 8**

- ❌ **容易翻车的说法**:(什么都不说,默认它会自己小心)
- 🌱 **刚开始、还没配规矩时(得多说几句)**:「删除文件、装新软件、联网下载之前,都先问我。」
- 💬 **配好规矩以后(像平时说话一样)**:「删文件一定要先问我,还要过审查。联网下载这种已经设了护栏,就不用每次说了。」
- 💡 **为什么能这么说**:删除写成规矩;下载、联网这类靠权限规则或钩子拦,设好一次就不用每次叮嘱。

卡片里出现的几个词:**UI**=界面,页面上你看到、点到的那些东西;**动效**=页面上的动画效果(比如点按钮时的过渡);**审到过**=审查有问题就改、改完再审,直到审查说「通过」;**立单 / 工单**=把需求、方案和进度写成一页清单(怎么把它写进规矩,见第 2 级最后一节);**审查**=请另一个 AI 来挑毛病(第 2 级);**子 agent**=CC 在对话里临时叫来帮忙的小助手(第 2 级);**钩子**=在特定时刻自动运行的检查脚本(第 1 级)。

### 看懂权限弹窗

**权限弹窗**是 CC 要改文件、跑命令、上网之前,弹出来问你「行不行」的那个框。

**先说实话**:就算开着「每步都问」的模式,新手多半也是一路点「同意」。这很正常——每条命令都要你判断,谁都判断不过来。

所以别指望每次都判断对。更靠谱的是两件事:

1. **认得几种危险的样子**,看到了就停下(下面的清单);
2. **把最危险的几种一次性设成自动拦下**,以后不靠你每次盯着(清单后面的「一次性设好自动拦」)。

#### 看到这些就停下

遇到下面任何一类,**先点拒绝**,然后问它:「这一步会删掉 / 覆盖 / 发出去什么?能不能先备份?」问清楚了再决定。

**1. 删东西**

- 长这样:`rm`、`rm -rf 文件夹`、`del`、`git clean -fd`;或者它说「我来清理一下没用的文件」。
- 为什么危险:删了就没了。电脑的回收站救不回命令删掉的文件,CC 的还原点也管不到。

**2. 覆盖或回退**

- 长这样:`git reset --hard`、`git checkout -- .`、`git push --force`(或 `git push -f`)、`> 文件名`(用 `>` 把内容写进一个已有的文件)、`mv 新文件 旧文件`(把同名文件盖掉)。
- 为什么危险:旧内容被新内容整个替换,或者没存档的改动被一笔抹掉。`--force` 还会把网上仓库里别人(或你另一台电脑)的提交冲掉。

**3. 动数据库**

- 长这样:命令或代码里有 `DROP`、`DELETE`、`TRUNCATE`;它说「重建一下数据库」「清空这张表」;或者要跑「迁移脚本」(migration,改数据库结构的程序)。
- 为什么危险:数据库里可能是你的真实数据,删了、改坏了,代码再怎么退回也找不回来。

**4. 碰密钥和配置**

- 长这样:要打开或修改 `.env`、`credentials`、带 `token` / `key` / `secret` 字样的文件,或者 `~/.ssh` 里的东西;或者要把它们的内容打印出来、贴到别处、发出去。
- 为什么危险:这些是你的「钥匙」(密码、通行码)。泄露了,别人就能用你的身份花你的钱、进你的账号。

**5. 往外发**

- 长这样:`git push`(把代码推到网上)、`npm publish`(把代码发布给所有人下载)、部署 / 上线命令、发邮件、发消息、调用按次收费的服务。
- 为什么危险:发出去就收不回来;收费的调用会真的花钱。

**6. 装东西、提权限**

- 长这样:`npm install 某个包`、`pip install`、`brew install`;`sudo`(用管理员权限运行);`chmod`(改文件权限);`curl 网址 | sh`(下载一段程序并直接运行)。
- 为什么危险:装进来的东西会在你电脑上运行;`sudo` 让命令能改动整台电脑;下载后直接运行,等于让陌生程序进门。

**7. 动系统和后台程序**

- 长这样:`kill`(结束一个程序;`kill -9` 是强行结束)、重启某个服务、改系统设置。
- 为什么危险:可能把你正在用的程序、或者一直在后台跑的服务弄停。

**8. 改到项目文件夹外面去**

- 长这样:要改的文件不在你这个项目文件夹里。常见的信号是路径以 `~/`(你的个人文件夹)或 `/`(从整台电脑的根目录算起)开头——但这只是信号,有时它们最后还是指向项目里面。拿不准就问它:「这个路径是在项目里面还是外面?」
- 为什么危险:你的需求只跟这个项目有关,项目外面的文件它没理由碰。

**这些一般可以放心点允许**:读文件、搜索文件;改的是这次说好的那几个文件;`git status`、`git log` 这类只看不改的命令。

**跑测试**要多问一句:测试本身也是程序,有的会写文件、动真实数据、联网。第一次跑某个项目的测试前,先问它「这个测试会不会写文件或者动真实数据?」,确认只在临时文件夹里折腾,再允许。

#### 一次性设好自动拦

清单记不住也没关系:把最危险的几种,写进设置文件,让 Claude Code 自动拦下。**这就是本仓反复讲的「把规矩写成会拦人的守卫」的入门版**——规矩不靠你每次记得,靠机器每次执行。

在你的项目里建一个文件 `.claude/settings.json`(也可以直接让 CC 帮你建,你确认内容),放进下面这段:

```json
{
  "permissions": {
    "deny": [
      "Bash(rm -rf *)",
      "Bash(git push --force *)",
      "Bash(git push -f *)",
      "Bash(git reset --hard *)",
      "Read(.env)",
      "Read(.env.*)",
      "Edit(.env)",
      "Edit(.env.*)"
    ],
    "ask": [
      "Bash(rm *)",
      "Bash(git push *)"
    ]
  }
}
```

意思是:

- `deny`(一律拒绝):强删文件夹(`rm -rf`)、强推、硬回退、读或改 `.env` 这类密钥文件,CC 直接做不了。CC 直接用 `cat .env` 这类命令去读,也会被同一条规则拦住。
- `ask`(必须问我):普通删除、推送,每次都会弹窗问你——**即使你开着自动模式**。
- **两条都命中时,拒绝优先**:规则按「deny → ask → allow」的顺序看,先命中哪条算哪条。所以 `rm -rf 文件夹` 会被直接拒绝,不会弹窗问你。
- 规则写法照官方文档:`Bash(...)` 管命令,`*` 代表「后面是什么都行」(也包括后面什么都没有,所以 `Bash(git reset --hard *)` 也拦光秃秃的 `git reset --hard`);`Read(...)` / `Edit(...)` 管读文件和改文件。`.env` 这样只写文件名的,管的是**你启动 CC 的那个文件夹及它下面每一层**的同名文件;上层文件夹里的 `.env` 不管——所以请在项目最外层启动 CC。

**要知道它的边界**:命令规则是**按命令的写法**匹配的,换个写法效果就变了:

- 换个参数顺序,比如 `rm -fr`:躲过了 `rm -rf` 那条「一律拒绝」,但还会被 `rm *` 那条「必须问我」拦下弹窗;
- 换个调用方式,比如 `/bin/rm -rf`、`bash -c '...'`、`git -C . push`:这几条规则就都拦不住了;
- 读 `.env` 的规则,拦得住 `cat .env` 这类点名读它的命令;但一个不点名、整个文件夹搜一遍的命令,或者它自己写的 Python / Node 小程序去读,不一定拦得住。

官方文档也明说:这类规则拦的是 CC 平常会写出的样子,不是一道真正的安全墙。所以它是「挡住大多数失手」,不是「万无一失」。

想要更硬的拦截:用**钩子**(PreToolUse hook,在每条命令执行前,先跑一段你自己写的检查程序,不合格就拒绝)。这一步可以以后再学,见官方文档 [hooks 指南](https://code.claude.com/docs/en/hooks-guide) 和 [permissions 说明](https://code.claude.com/docs/en/permissions)。

#### 权限模式

- 状态栏看模式:CLI 底部的状态栏会显示当前模式(比如 `⏸ manual mode on`、`⏵⏵ auto mode on`);桌面版看发送按钮旁边的模式选择器。
- **Manual(手动)**:大多数改文件、跑命令、联网的动作都会先问你。**Auto(自动)**:日常弹窗少了很多,改由另一个 AI 在执行前替你审一遍;你设过的 `ask` 规则照样弹窗。新版本在条件满足时默认就是 Auto。
- 名字里带 **bypass / skip permissions**(跳过所有权限检查)的模式和选项:**新手别碰。**

#### 弹窗里怎么选

- **允许一次**:最稳的「同意」。
- **允许并且以后不再问**:CLI 里对命令选这一项,会**按「这个项目 + 这条命令」一直记住**。**别对上面清单里的任何一类选这个。** 只对 `git status` 这种只看不改、你确定永远放心的命令用。
- **拒绝**:拒绝永远是安全的。拒绝后它会停下,你可以告诉它为什么不行、该怎么做。

**做到什么程度算会了**:你连续几次提需求,CC 都没有「顺手」多改东西;它说完成时都能拿出证据;看到「停下清单」里的样子你会先拒绝再问;项目里放好了那段自动拦的设置。

**什么时候该上第 1 级**:你发现自己**每次开新对话都要重复交代同样的话**(「别动文章内容」「改之前先问我」)。

## 第 1 级 · 一个 CLAUDE.md

**适合谁**:已经习惯和 CC 对话,开始厌烦每次都重复同样的叮嘱。

**这一级做什么**:在项目里放一个 `CLAUDE.md` 文件。

### CLAUDE.md 是什么

它是一个放在项目根目录(项目最外层的文件夹)里的普通文本文件。**CC 每次开始新对话,都会自动读它。** 你写在里面的话,就不用每次重说了。

**但它不是一道锁。** CLAUDE.md 里的话是写给 CC 看的「叮嘱」,CC 会尽量照做,但不保证百分之百。真正不许发生的事(比如删文件、推送到网上),要靠权限设置来拦:在设置里写「这类命令必须问我 / 一律拒绝」的规则,或者用钩子(hooks,在特定时刻自动运行的检查脚本)。怎么写这些规则,让 CC 帮你写、你确认,细节见官方文档的权限(permissions)一页。

起步很简单:

1. 复制本仓的[入门版模板 `templates/CLAUDE.beginner.md`](../templates/CLAUDE.beginner.md),放到你的项目里,改名为 `CLAUDE.md`;
2. 把里面带 `<尖括号>` 的地方改成你自己的内容。

也可以在 CC 里输入 `/init`,让它看一遍你的项目,自动生成一份初稿,你再删改。

### 怎么让它长大:被坑一次,加一条

**不要一开始就写一大堆规矩。** 好的规矩都是踩过坑才长出来的:

- 它某次把你的文章内容改乱了 → 加一条「文章内容(`posts/` 文件夹)永远不要改,除非我明确说」;
- 它某次没验证就说完成了 → 加一条「说完成之前,必须给出验证的命令和输出」。

每条都写得**具体到能判断对错**。「要小心」这种话没用;「删除任何文件前先问我」才有用。官方建议每个 CLAUDE.md 保持在 200 行以内——太长了它反而记不住重点。

### memory 和 CLAUDE.md 有什么不一样

CC 还有一个「自动记忆」(auto memory):它在干活过程中,自己把觉得有用的东西记成笔记(比如你纠正过它的地方),下次对话会读到。在 CC 里输入 `/memory` 可以查看和编辑。

| | CLAUDE.md | 自动记忆 |
|---|---|---|
| 谁写 | 你 | CC 自己 |
| 放什么 | 规矩、要求 | 它学到的经验、你的偏好 |
| 在哪 | 你的项目里 | 你电脑上,按项目分开存(具体位置以官方文档为准) |

**建议**:**重要的规矩写进 CLAUDE.md;绝对不许发生的事,再加一道权限规则。** 自动记忆是它自己的笔记,你不一定每条都看过;CLAUDE.md 是你写给它的明文规定,你清楚里面写了什么。

**做到什么程度算会了**:你的 CLAUDE.md 有 5–10 条规矩,每条背后都能说出「是哪次被坑才加的」;新开对话后不用再重复叮嘱。

**什么时候该上第 2 级**:改动开始变多,你**担心改坏了回不去**;或者你看不懂它写的代码,**没办法判断它做得对不对**。

## 第 2 级 · git + 测试 + AI 互审

**适合谁**:项目开始有点规模,不想再靠运气。

**这一级做什么**:学会三件「保险」——存档、自动检查、找第二个 AI 来审。**你不用自己学会敲这些命令,让 CC 帮你做,你只要知道每一步是什么意思。**

### git:给项目存档

**git** 是一个「存档工具」,用来记录项目的每一个版本。只需要懂三个词:

- **提交(commit)**:存一个档。以后随时能回到这个档。
- **分支(branch)**:从当前存档复制出一条「平行草稿线」。在分支上随便改,主线不受影响;改好了再合回主线。
- **回退**:回到之前的某个存档。

让 CC 帮你做,可以这样说:

- 「帮我把这个项目变成 git 仓库,先提交一次当前状态。」(背后是 `git init`、`git commit`)
- 「开始改之前,先新建一个分支,名字叫 dark-mode。」(背后是 `git switch -c dark-mode`)
- 「这一步做完、我确认没问题了,帮我提交一次,说明写清楚改了什么。」
- 「列出最近 10 次提交。」(背后是 `git log --oneline -10`)
- 「刚才那次提交有问题,用不丢历史的方式撤销它。」(背后是 `git revert`)

**两条要盯住的**:

- 看到 `git reset --hard`、`git push --force`、`git clean` 这类命令,**先拒绝,问清楚**。它们会真的丢掉东西。
- `git push`(把代码推到网上的仓库,比如 GitHub)前先问你——加进你的 CLAUDE.md。

**PR(Pull Request,合并请求)**:如果你的代码放在 GitHub 上,分支改好后,可以开一个「合并请求」,请求把分支合回主线。它的好处是合并前能先看清改了什么、让别人(或另一个 AI)审一遍。一个人的小项目,不开 PR 也行。

### 测试:让检查自动跑

**测试**是一小段专门用来检查代码的代码。比如「输入 3 笔账,总额应该是 60」。以后每次改动后跑一遍测试,原来好的功能有没有被改坏,一眼就知道。

可以这样说:

- 「给『记一笔』这个功能写测试,包括正常输入和金额为空的情况。」
- 「跑一遍全部测试,把结果原样贴给我。」
- 「改完之后再跑一遍测试,告诉我通过了几个、失败了几个。」

**看结果时看这几样**:

- 真的跑了吗?(有没有贴出命令和输出原文)
- 跑的是哪些测试?是不是只挑了一小部分?
- 通过几个、失败几个、**跳过**几个(跳过的等于没测);
- 最后有没有报错退出。

它说「测试都通过了」,让它把输出原样贴出来,你自己对一眼。

### AI 互审:请第二个 AI 来挑刺

同一个 AI 审自己写的东西,很容易「自己说服自己」。请另一个 AI 来审,能挑出它自己看不到的问题。

**什么时候值得审**:

- 改动比较大,或者改坏了很难恢复;
- 你看不懂代码,没办法自己判断;
- 它说「完成了」,但你心里不踏实。

改一个字这种小事,不用审。

**怎么审**:最省事的办法,是在 CC 里让它派一个「子 agent」(它在对话里临时叫来的帮手)当审查员:

> 「派一个审查员(子 agent),只读不改,审查这次的改动:有没有超出我要求的范围、有没有没验证就说完成的地方、有没有可能改坏别的功能。让它列出问题和证据。」

想要更强的对抗,可以请另一家的 AI(比如 OpenAI 的 Codex)来审。完整做法见本仓的[互审专题](workflow.md)和[机看版说明](../for-claude-code.md)。

审查意见回来后,**不要全盘照收**:让 CC 逐条说「同意 / 不同意,理由是什么」,改完再审一次。

### 把工单和审查写进 CLAUDE.md:以后一句话就够

这一级学会的东西,最后都要写进 CLAUDE.md。写进去以后,第 0 级那些「配好规矩以后」的说法才能用。

**工单**:一页写着「要做什么、打算怎么做、做到哪一步了」的清单,放在项目里的一个文件里。本仓有现成的[工单模板](../templates/ticket.md),入门时可以只留「原话」「要做什么」「怎么验证」「状态」几栏。

**第一步,先把模板放进你的项目**:把本仓的 `templates/ticket.md` 复制到你项目里的 `templates/ticket.md`(没有 `templates` 文件夹就新建一个),再建一个空的 `tickets/` 文件夹放以后的工单。也可以直接让 CC 帮你做。

**第二步**,让 CC 帮你在 CLAUDE.md 里加这样几条(按你的项目改):

```markdown
- 要改代码,先立单:在 tickets/ 文件夹里按 templates/ticket.md 建一个工单,写清要做什么、怎么验证,给我看过再动手。
- 做的过程中,每完成一步就更新工单里的「状态」。我问进度时,按工单逐项回答。
- 改完后,派一个只读的审查员(子 agent)审这次改动;审查有问题就改,改完再审,直到审查说通过(「审到过」)才算完成。
- 从零做一个功能前,先搜一下有没有现成的开源方案或教程,把找到的写进工单。
```

写进去以后,你说「要改代码就先立单,改完给审查审到过」,它就知道整套该怎么走。

**做到什么程度算会了**:每次动手前都在分支上;每个功能都有测试;大改动都过了一次互审;改坏了你知道怎么让它退回上一个存档。

**什么时候该上第 3 级**:见下一级开头的信号。

## 第 3 级 · 多窗口并行

**适合谁**:一个对话已经不够用,想同时开好几个 CC 窗口干不同的活。

**先看信号。出现下面两条以上,才说明你需要这一级:**

- 一个对话里塞了好几件互不相干的事,上下文越来越乱;
- 经常要等它干完一件,才能开始下一件,而这几件其实互不影响;
- 你开始在两个窗口之间**来回复制粘贴**,传话、对进度;
- 两个窗口改了同一个文件,互相覆盖;
- 第二天想不起来哪个窗口做到哪了。

如果只是「想快一点」,先别上。多窗口会多出一整层协调成本。

**这一级的关键概念:worktree。** **worktree**(工作树)是 git 提供的功能:同一个项目,复制出几份互不干扰的工作目录,每份在自己的分支上。每个窗口在自己的 worktree 里干活,就不会互相覆盖文件。

- **CLI**:用 `claude -w <名字>`(也就是 `claude --worktree <名字>`)启动,CC 会自动建一个 worktree 并在里面工作。
- **桌面版**:新建会话时,在分支名旁边勾选 **worktree** 选项。

**窗口之间传话**:CC 自己就能给你电脑上的其他 CC 会话发消息,不用你复制粘贴(CLI 和桌面版的具体做法见下一节)。

**怎么组织多个窗口**——总调度、派活、认领文件、排号、谁负责合并——这些都在[进阶手册](idea-to-merge.md)里:第 8–10 章,以及规则库 A13(总调度打法增补)和[流程图 ③](flowcharts.md)。**等你真的到了这一级,再去读。**

**做到什么程度算会了**:每个窗口有自己的 worktree;窗口之间靠 CC 传话,不靠你复制粘贴;同一个文件同一时间只有一个窗口在改。

## CLI 还是桌面版

**它们是同一个 Claude Code。** 官方文档说,桌面版用的是和 CLI 同一套底层引擎,只是有图形界面;两者可以在同一台电脑、同一个项目上同时用。下面这些是**共用**的:

- 项目里的 `CLAUDE.md`(和 `CLAUDE.local.md`);
- 设置文件(`~/.claude/settings.json` 等),包括**权限规则**;
- 钩子(hooks,在特定时刻自动运行的脚本)和 skill(技能包:写好的一套做事步骤,CC 在合适的时候自动加载);
- MCP 服务器(给 CC 接上外部工具)。

**自动记忆**按项目存在你的电脑上;两边是不是读同一份,以官方文档为准。

**差别主要在「看」和「操作」:**

| | 桌面版 | CLI(终端) |
|---|---|---|
| 看改动 | 有改动对比面板(diff 视图),可以逐行点评 | 在对话里看文字 |
| 看效果 | 内置浏览器面板,可以直接预览你的网页 | 自己开浏览器 |
| 多个会话 | 侧边栏,点一下切换 | 开多个终端窗口;或者用 `claude --bg` 把会话放到后台跑,用 `claude agents` 一屏看所有后台会话,用 `claude attach <id>` 进入某个会话 |
| worktree | 新建会话时勾选 worktree 选项 | `claude -w <名字>`;再加 `--tmux` 可以同时开一个 tmux 窗口(tmux 是一个终端分屏工具) |
| 权限模式 | 发送按钮旁边的模式选择器 | `Shift+Tab` 切换;还有一个 `dontAsk` 模式(没事先允许过的动作一律不做、也不问你)只有 CLI 有 |
| 设置类命令 | 少数会弹出终端面板的命令(比如 `/permissions`)不能用,要直接改设置文件,或者到 CLI 里运行 | 都能用 |
| 脚本、自动化 | 不支持 | 支持(`claude -p` 等) |

**会话之间互相发消息:两边都能,但不完全是同一套机制。**

- **CLI**:CC 可以给你电脑上的其他 CC 会话发消息,默认开启,不用设置。
  - 你只要说一句「告诉另一个窗口:数据库结构改了」,它自己去发。
  - 想指定发给谁,在话里打 `@` 加会话名。
  - 输入 `/list-agents`(也叫 `/peers`)可以检查这个功能在不在。
  - 版本要求(以官方文档为准):发消息要 v2.1.224 起(Windows 原生 v2.1.234 起);用 `@会话名` 指定对象要 v2.1.232 起;用第三方云平台接入 Claude 的,还要 v2.1.248 起。
- **桌面版**:有自己的「跨会话」功能,可以查看、给桌面版里的其他会话发消息(消息会显示成一张带来源的卡片)。但这个功能**只看得到桌面版自己开的会话**,看不到你在终端里开的 CLI 会话。要和 CLI 会话互相发消息,走的是上面那套通用的跨会话消息。

**怎么选**:想在一个窗口里管好几个会话、想直观地看改动和预览效果 → 桌面版;习惯终端、想写脚本自动化 → CLI。两边可以混着用;CLI 里输入 `/desktop`,可以把当前会话搬到桌面版接着做(有平台和登录方式的限制,以官方文档为准)。

flowchart TD
    A["第 0 级:会说话"] --> B{"总在重复叮嘱?"}
